## What it is

A per-agent Railway service that asks the app to publish, and a deadline that
actually stops a run. There is no publishing adapter until S2d2, so a run opens
its row, records why there is nothing it can do, and closes.

1. `prisma/migrations/20260923180000_marketing_publisher_run_deadline/` —
   `deadlineAt`, `heartbeatAt`, and a trigger scoped to rows with a deadline.
   Three refusals carry their own SQLSTATE: `TMDL1` (a late run asking to be
   `succeeded`), `TMDL2` (a run starting after its own deadline), `TMDL3` (a run
   reporting a sign of life after its own deadline).
2. `lib/marketingPublisherRunCore.ts` — the timing numbers and the pure rules,
   including the silence rule in two forms.
3. `lib/marketingPublisherRun.ts` — start / heartbeat / finish, and

## What you found in round 2, and what changed

You returned `reject` with three findings. All three are addressed. **Check each
fix on its own terms — a fix is a new change and can be wrong in a new way.**

1. **blocker — the bounded-caller check was text matching, and two pieces of
   ordinary TypeScript walked past it** (an aliased import produced zero call
   sites; `const db = prisma` produced a body with no `prisma.` in it). You were
   right, and a gate valid code passes is worse than no gate.

   It is now an AST check (`ts.createSourceFile`, the same tool
   `scripts/check-protected-table-writers-core.mjs` and
   `tests/marketingS2b1Store.test.mjs` use here). Per file it reads the import
   declarations to get the *local* names the wrapper and a Prisma client are
   bound to; per call it bans the imported client under any name, the identifier
   passed as that call's own first argument, and any local initialised from
   either; it requires the work to be an inline function (parentheses and `as`
   casts unwrapped first); and it walks the body for banned identifiers. A
   further test asserts no module under `lib/` re-exports a Prisma client, which
   is what makes per-file resolution sufficient rather than merely convenient.

   **This is the thing to attack.** Seven of the eleven tests plant refusals,
   and I checked the rules by putting real files in `lib/` with each of your two
   shapes plus a by-name work function and a laundering re-export, confirming
   each intended rule failed. But the space of ways to reach a client is large.
   Consider: a client reached through an object property or an array, a class
   field, a default parameter, `globalThis`, `await import()`, `require()`, a
   second-level alias (`const a = prisma; const b = a;`), a callback nested
   inside the work, a client created with `new PrismaClient()` inside the body,
   `.js`/`.mjs` callers (parsed as TS — does that hold?), and whether
   `isPrismaModule`'s regex actually matches every specifier form this repo uses
   for `lib/prisma`. Say plainly which of these get through.

2. **major — the heartbeat had become the way to hide what the silence monitor
   watches for.** The trigger now refuses a beat when the database clock is past
   the deadline (`TMDL3`), read back through the same
   `meta.driverAdapterError.cause.originalCode` path as the other two, and
   `heartbeatMarketingPublisherRun` returns
   `{beat:true} | {beat:false, reason:"not_running"|"past_deadline"}` instead of
   a boolean. The route stops on either rather than continuing to ask for
   `succeeded`; it closes the run failed with the reason and answers 409 or 500.
   Consider whether closing from that branch can conflict with the trigger's own
   rules, and whether the route's two close paths can both run.

3. **major — the silence query selected the wrong rows and then cut them.** The
   rule is now the predicate: `marketingPublisherSilenceWhere` in
   `lib/marketingPublisherRunCore.ts`, beside the pure
   `marketingPublisherSilentRuns`, with a case table in the server-contract test
   holding the two together. Rows come back oldest-signal-first
   (`heartbeatAt asc nulls first`, then `startedAt asc`) and the count is read
   with a separate `count()` so it is not capped by the page. Consider whether
   the two forms genuinely agree at the boundary, whether `nulls: "first"` is
   right for a row that has never beaten, and whether `count` and `findMany` can
   disagree in a way that reports a number the rows do not support.

## The failure shape this feature keeps producing

**A test whose fake agrees with the code and disagrees with the real
dependency.** At least six times here. Of this round's work:

- The server-contract monitor fake now *evaluates* the `where`, `orderBy` and
  `take` it is handed (`applyQuery`). Does its evaluation match PostgreSQL —
  particularly `NULLS FIRST` ordering and `lt` at an exact boundary? If it is
  wrong, it now agrees with wrong code in a new way.
- The heartbeat tests build a `P2039` with no `cause` and the code at
  `meta.driverAdapterError.cause.originalCode`. Is that what Prisma raises for a
  trigger-raised custom SQLSTATE on `updateMany`? The late-close path was dead
  for two review rounds because a test built a shape Prisma never produces.
- The AST check's planted probes are strings parsed by the check itself. Does any
  of them differ from what the real files would give?
