## The rest of the slice, which is where the remaining risk is

In round 4 you confirmed the trigger and the silence query are right for the
questions that round asked. The remaining surface is worth a fresh look now that
the guard is no longer the story:

1. **The migration.** Walk every path: insert with and without a deadline; update
   while running (heartbeat, close on time, close late, close failed); update
   after closing; attempts to add, move or null a deadline. Can a late run be
   recorded `succeeded` by any route? Can it break an existing scheduled job that
   writes `ScheduledJobRun` without a deadline — `completeScheduledJob`,
   `failScheduledJob`, the auto-fix fields?
2. **`runBoundedMarketingTransaction`.** It refuses below PostgreSQL 17, and
   refuses when a `transaction_timeout` is already running because 17 starts a
   timer only when none is active. Is the refusal right, are `0` and `0ms` the
   only spellings of off, and does the ordering of the three timeouts keep all
   three armed?
3. **The route.** Bearer comparison, body strictness, the deadline window,
   duplicate run ids, and the two close paths — can both run? The route judges the
   deadline with the process clock and the trigger with the database's; where does
   that land?
4. **The service.** Does the supervisor kill in every case, including a worker
   that ignores signals or never spawns? Does anything retry? Can either hold
   anything beyond `MARKETING_PUBLISH_SECRET` and `MARKETING_PUBLISH_URL`?
5. **The tests.** The recurring failure in this feature is **a test whose fake
   agrees with the code and disagrees with the real dependency** — it has happened
   eight times. Is the `P2039` shape the heartbeat reads what Prisma actually
   raises for a trigger-raised custom SQLSTATE on `updateMany`? Would each new
   integration case actually have failed the version it was written against?
