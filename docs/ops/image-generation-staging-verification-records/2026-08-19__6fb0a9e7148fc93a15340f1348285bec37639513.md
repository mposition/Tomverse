## 런타임 판정 — provider별 예산 귀속 (핵심)

배포가 바뀌었으므로 대상 SHA도 바뀌었습니다. 이 절은 **`6fb0a9e`**에 대한

### 왜 이 실행이 결함을 판별하는가

**세 provider 모두 true-up이 발생했습니다.** 하나라도 true-up이 없었다면 옛
코드와 새 코드가 같은 값을 냈을 것이고 판별이 되지 않았습니다.

옛 코드는 환급을 openai 키로 고정했으므로, xai·fal의 true-up 12,000이 openai
버킷에서 빠졌어야 합니다.

```
              옛 코드 예측     관측
openai        41,055          53,055
xai           55,000          50,000
fal           87,000          80,000
```

세 값 모두 다릅니다. 각 버킷은 **자기 예약에서 자기 true-up만** 뺀 값입니다.

그리고 xai·fal의 true-up 합계 **5,000 + 7,000 = 12,000**은 2026-08-16
production에서 openai 월 버킷이 정산 합계보다 모자랐던 값과 같습니다. 그때의
진단을 사후에 확인해 줍니다.

데이터 손실이 아니고 과금에도 영향이 없습니다. 원인은 규명하지 않았습니다 --
치수 기록이 실패했는지, 그 세대가 치수를 낼 수 없는 경로였는지 구분하려면
해당 행을 봐야 합니다.

### 발견-2 — staging 예산이 floor에 붙어 있고 두 provider가 advisory를 띄운다

```
openai  day 10,800,000  month 10,800,000   month_not_above_day
xai     day 10,800,000  month 10,800,000   month_not_above_day
fal     day 12,000,000  month 50,000,000   -
```

**결함이 아니라 설정입니다.** `lib/imageProviderBudget.ts`의 해당 주석이
이렇게 적습니다 -- *"작은 동일 쌍이 총지출을 묶으므로 staging에서는 의도적이고,
production에서는 대개 둘 중 하나를 복사한 것"*. production에서는 이 상태가
2026-08-16에 실제로 결함이었고 정정됐습니다.

기록하는 이유는 다음 회차가 이것을 결함으로 다시 보고하지 않게 하기 위해서이며,
동시에 **staging의 일·월 창이 사실상 하나**라는 사실이 남은 항목(예산 소진
경로)을 검증할 때 전제가 되기 때문입니다.

## 격리 실행 — provider당 한 건씩, 사이마다 스냅샷

앞 절의 실측은 **세 건을 실행한 뒤 한 번 읽은 것**입니다. 각 버킷의 값이 자기
정산액과 같다는 것까지는 말하지만, *다른 버킷이 움직이지 않았다*는 것은 총합에서
유추한 결과입니다. 옛 결함은 정확히 "다른 버킷이 움직인다"는 형태였으므로, 그
부분이 유추로 남아 있으면 판별의 결정적 고리가 관측이 아닙니다.

이 절은 **한 건씩 실행하고 사이마다 `GET /api/admin/image-generation`을 읽어**
그 유추를 관측으로 바꿉니다. 기준선은 앞 절이 끝난 상태입니다.

```
기준선 (succeeded 12)   openai 53,055   xai 50,000   fal 80,000
                        reserved 890,000   settled 708,525
```

### 단계 1 — OpenAI (gpt-image-2, Standard / 1024×1024)

| 버킷 | 이전 | 이후 | 증가 |
|---|---|---|---|
| openai `usedTodayMicroUsd` | 53,055 | **106,110** | +53,055 = 자기 정산액 |
| xai | 50,000 | 50,000 | 0 |
| fal | 80,000 | 80,000 | 0 |

`reserved` 890,000 → 948,000 (+58,000 = openai 최악 원가), `settled` 708,525 →
761,580 (+53,055). true-up 4,945가 openai에서 빠졌습니다. succeeded 12 → 13.

### 단계 2 — xAI (Grok Imagine, Standard / 1024×1024)

| 버킷 | 이전 | 이후 | 증가 |
|---|---|---|---|
| **openai** `usedTodayMicroUsd` | 106,110 | **106,110** | **0 ← 판별점** |
| xai | 50,000 | **100,000** | +50,000 = 자기 정산액 |
| fal | 80,000 | 80,000 | 0 |

`reserved` 948,000 → 1,003,000 (+55,000 = xai 최악 원가), `settled` 761,580 →
811,580 (+50,000). xai 월 버킷 160,000 → 210,000. succeeded 13 → 14,
`failuresByPhase` 비어 있음, invariant 6종 전부 0, 저장소 원본 14 · 썸네일 14.

**이 한 줄이 이 회차 전체가 만들려던 관측입니다.** xai 예약 55,000에 정산
50,000이므로 true-up 5,000이 반드시 어딘가에서 빠집니다. 옛 코드는 환급 키를
openai로 고정했으므로 openai가 106,110 → 101,110이 됐어야 합니다. 움직이지
않았고, 대신 xai가 자기 정산액만큼만 올랐습니다.

### 단계 3 — fal (Nano Banana 2, Standard / 1024×1024)

| 버킷 | 이전 | 이후 | 증가 |
|---|---|---|---|
| openai `usedTodayMicroUsd` | 106,110 | 106,110 | 0 |
| xai | 100,000 | 100,000 | 0 |
| fal | 80,000 | **160,000** | +80,000 = 자기 정산액 |

`reserved` 1,003,000 → 1,090,000 (+87,000 = fal 최악 원가), `settled` 811,580 →
891,580 (+80,000). true-up 7,000이 fal에서 빠졌습니다. fal 월 버킷 254,000 →
334,000. succeeded 14 → 15, `failuresByPhase` 비어 있음, invariant 6종 전부 0,
저장소 원본 15 · 썸네일 15.

fal은 세 provider 중 true-up이 가장 큽니다(7,000). 옛 코드였다면 openai가
106,110 → 99,110이 됐어야 합니다.

### 격리 실행 종합

```
              예약      정산      true-up   버킷 증가   다른 버킷
openai        58,000    53,055     4,945     +53,055    xai 0 · fal 0
xai           55,000    50,000     5,000     +50,000    openai 0 · fal 0
fal           87,000    80,000     7,000     +80,000    openai 0 · xai 0
합계         200,000   183,055    16,945
```

`reserved` 890,000 → 1,090,000 (+200,000), `settled` 708,525 → 891,580
(+183,055). 앞 절의 일괄 실행과 같은 수이며, 이번에는 **각 단계에서 다른 두
버킷이 움직이지 않는 것을 직접 봤습니다.** 2026-08-16 결함은 이 빌드에
없습니다.

고정가 상한도 세 건 모두 지켜집니다 — openai 53,055/70 = 758, xai 50,000/75 =
667, fal 80,000/120 = 667 µUSD/크레딧으로 상한 900 아래입니다.

`dimensionCoverage`는 xai 4/4, fal 4/4, openai 7/6입니다. openai 격차는 이
회차 내내 **1로 고정**이며 6건 모두 측정됐으므로, 발견-1은 과거 1건이고 늘어나지
않습니다.

## 발견-3 — 2026-08 drift가 정확히 닫힌다 (그리고 예약 2건이 어느 invariant에도 안 걸린다)

이 스냅샷은 앞 절이 "약 12,000"으로 남겨 둔 drift를 **정확한 수로** 닫습니다.
아래는 보고된 값만으로 하는 산술이며 행을 열어 본 것이 아닙니다.

예약 총액이 provider별 최악 원가로 정확히 떨어집니다.

```
openai  9 x 58,000 = 522,000     (정산 7건 + 정산 없는 2건)
xai     4 x 55,000 = 220,000
fal     4 x 87,000 = 348,000
합계               1,090,000     = reservations.reservedCostMicroUsd
```

`reservations.total`은 17이고 성공한 generation은 15, 실패는 0입니다. 즉
**generation이 하나도 없는 예약이 2건** 있고, 위 분해가 정확히 맞으려면 둘 다
openai이며 최악 원가 58,000을 그대로 들고 있어야 합니다 — 합계 116,000.

월 버킷의 초과분도 같은 116,000입니다.

```
provider  월 버킷    정산 합계   초과
openai    463,580    371,580    +92,000
xai       210,000    200,000    +10,000
fal       334,000    320,000    +14,000
합계                            116,000
```

그리고 그 초과가 어떻게 갈라졌는지가 결함의 서명입니다. 오늘 실행한 6건(provider당
2건)은 전부 이 빌드에서 자기 버킷으로 정산됐으므로 초과에 기여하지 않습니다.
남는 것은 오늘 이전의 xai 2건 · fal 2건이고, 그 true-up이

```
xai   2 x 5,000 = 10,000        <- xai 초과와 일치
fal   2 x 7,000 = 14,000        <- fal 초과와 일치
합계             24,000
openai  116,000 - 24,000 = 92,000   <- openai 초과와 일치
```

**옛 코드가 xai·fal의 true-up을 openai 버킷에서 환급했다**는 것과 정확히 같은
모양입니다. 앞 절의 "약 12,000"은 한 쌍만 센 값이었고, 실제로는 오늘 이전에 두
쌍이 있었습니다.

두 가지가 남습니다.

1. **정산도 환급도 없는 예약 2건(116,000 µUSD)을 어느 invariant도 잡지
   않습니다.** `staleGenerations`·`strandedSettlements`가 0인데 이 둘은
   generation과 settlement에 대한 검사이고, *generation이 없는 예약*은 그
   어느 쪽도 아닙니다. staging에서는 예산의 1%지만 같은 모양이 production에서
   생기면 provider 예산을 조용히 소모합니다. **행을 열어 확인해야 확정입니다**
   — 위는 보고된 합계에서의 추론입니다.
2. **월 경계는 이 116,000을 지우지 않고 효과만 끝냅니다.** 처리는 여전히
   `completed` / `accepted` / `pending` 중 하나를 명시하는 일이며, 이제
   `accepted`로 적을 경우 받아들이는 금액이 무엇인지가 확정됐습니다.

## 이 회차가 덮지 않은 것

- 재시도(같은 target 새 attempt), 취소, 동시성 한도
- 예산 소진 시 `PROVIDER_BUDGET_EXHAUSTED` 경로
- Guest·Free 잠금 노출, Pro/Max 게이트
- 모바일 320px, ko/en 두 locale
- 사전 조건 전체(migration 선후, 검증 계정, 정리 담당자)
- 멀티 모델 fan-out — 세 건 모두 **단일 모델** 그룹입니다. 핵심 계약인
  `modelIds` 복수 POST는 이 회차에서 실행하지 않았습니다
- production에서의 재확인 — 이 판정은 staging의 `6fb0a9e`에 대한 것이고
  production은 `ae649be`입니다
