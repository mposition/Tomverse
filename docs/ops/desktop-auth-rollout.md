# Tomverse Desktop authentication rollout

Follow the [dev, Test, and production release lanes](dev-test-lanes.md). Deploy the server routes and repository migrations with the Desktop flags off. Migration `20261122100000_desktop_native_device` adds `desktop` to the existing device platform check. The server uses the existing native signing and refresh configuration, and the existing Tomverse login email delivery and Turnstile configuration.

| Server variable | Purpose |
| --- | --- |
| `TOMVERSE_DESKTOP_AUTH_ENABLED` | Enables Desktop authentication routes and requires a ready native keyring. |
| `TOMVERSE_DESKTOP_EMAIL_LOGIN_ENABLED` | Enables requesting and verifying codes and serving the Turnstile page. |
| `TOMVERSE_DESKTOP_ACCOUNT_SETTINGS_ENABLED` | Enables the separate in-app account settings session. |
| `TOMVERSE_DESKTOP_SOCIAL_LOGIN_ENABLED` | Lets Desktop Settings add Google or Microsoft as a login method (`desktopSocialLink` capability, listing only providers whose `GOOGLE_ID`/`GOOGLE_SECRET` or `AZURE_AD_CLIENT_ID`/`AZURE_AD_CLIENT_SECRET`/`AZURE_AD_TENANT_ID` this server holds). Requires Desktop authentication and the account settings session. Adding a method needs a recent sign-in (`TOMVERSE_DESKTOP_RECENT_AUTH_ENABLED`, as removal does). The provider's page opens in the system browser with PKCE and a signed state; it returns to the callback already registered for the web link flow (`/api/user/login-methods/oauth/callback`), so **no new redirect URI is needed at Google or Microsoft**. Signing in to Desktop with Google, Microsoft or Apple needs no switch beyond `TOMVERSE_DESKTOP_AUTH_ENABLED`. |
| `TOMVERSE_DESKTOP_BILLING_ENABLED` | Shows Desktop's in-app plan, purchase, plan-change, cancellation and refund screens (`desktopBilling` capability). Requires the account settings session. It is a display switch: the billing routes already accept that session as they accept a web session. Off, Desktop's Plan tab shows balances only. |
| `TOMVERSE_DESKTOP_REMOTE_CONTROL_ENABLED` | Enables control of a PC's Desktop Code tasks from the account's other signed-in devices at `/remote` (`docs/ops/desktop-remote-control.md`). Requires Desktop authentication and migration `20261126120000_desktop_remote_control`. The PC sends nothing until the person also turns it on in Desktop settings. |
| `TOMVERSE_DESKTOP_REMOTE_PASSKEY_ENABLED` | With remote control on, lets an account register passkeys (WebAuthn) at `/remote`; an account that has one confirms "Allow once" and follow-ups with it (`docs/ops/desktop-remote-control.md`). Requires migration `20261128070000_desktop_remote_passkey`. Off: nobody is asked for a passkey and none can be registered. |
| `TOMVERSE_DESKTOP_REMOTE_PREVIEW_ENABLED` | With remote control on, lets a PC report the line counts of a file change waiting for approval, and a few redacted changed lines when its person turned that on in Desktop settings (`docs/ops/desktop-remote-control.md`). Off: the capability is not named and the server drops those fields from a report. |
| `TOMVERSE_DESKTOP_VOICE_ENABLED` | Enrols `POST /api/chat/voice-transcription` and `POST /api/chat/voice` for the Desktop bearer (`desktopVoiceInput` and `desktopVoiceConversation` capabilities). Requires Desktop Chat writes. Each route keeps its own switch and limits: dictation needs `feature.voiceInputEnabled` and spends the voice seconds budget, with no credits charged; the Chat voice conversation needs `VOICE_CONVERSATION_ENABLED`, its key and the Voice Recovery worker, and charges 36 credits per connected minute exactly as on the web. Desktop uses dictation in Chat, Review and Code (also as a spoken instruction that is sent at once), and the two-way conversation in Chat only: the route refuses a Review or a locked conversation. |
| `TOMVERSE_DESKTOP_PLUGINS_ENABLED` | Shows Desktop's in-app connector management and the Chat connector picker (`desktopPlugins` capability). Requires the account settings session and `MCP_CONNECTOR_PREVIEW_ENABLED`. It is mostly a display switch: the `/api/mcp` routes already accept that session as they accept a web session. The one Desktop bearer read it opens is `GET /api/mcp/providers`, the web Plugins page's platform catalogue (no account data; sign-in, rate limit, ETag and `Cache-Control: private, max-age=600, must-revalidate`), named to the app by the `desktopPluginCatalog` capability so the Plugins screen lists the same platforms as the web, and a platform added to the web appears without a new app. An older server names no such capability and the screen lists that server's own connectors only. |
| `TOMVERSE_DESKTOP_REASONING_STEPS_ENABLED` | Adds the middle reasoning step (`medium`) beside Low and High for the two models that take an effort, for a Desktop Chat or Review turn (`desktopReasoningSteps` capability; the public catalogue lists it in `reasoningEffortSteps` and keeps `reasoningEfforts` as it was) and for the coding API (`tomverse.reasoning_efforts`, `tomverse_effort`), which Desktop Code and the CLI read from the catalogue. Needs `TOMVERSE_REASONING_EFFORT_ENABLED`. The web composer is unchanged: a web request for `medium` is refused with 409. No price changes: credits come from the model's own weight, not from the step. |
| `TOMVERSE_DESKTOP_PROMPT_REFINER_ENABLED` | Lets a Desktop Auto Chat turn carry the Prompt Refiner decision the server holds (`desktopPromptRefiner` capability, also requires `promptRefinerChatExecutionRelease().autoEnabled`). Needs Desktop Chat writes and the account settings session. The Refiner stays automatic and server-owned: Desktop writes the typed text as the conversation's composer draft, takes a scope, asks for one `prepare`, saves the question under the request id the server returned and sends only the decision; the release authority, kill switch, budget and one-time consume are unchanged. Changing this code changes the Chat release source fingerprint, so the Owner re-activation that any chat route change needs applies here too. |
| `TOMVERSE_DESKTOP_PLUGIN_SOURCES_ENABLED` | Lets Desktop's Plugins screen install a plugin from a zip file, an address of a zip file, an npm package or a private GitHub repository (read with the person's own GitHub CLI sign-in), and adds the Tomverse official marketplace the app carries (`desktopPluginSources` capability). Default off. Requires only the Desktop session: local plugins do not use the connector routes, so it is independent of `TOMVERSE_DESKTOP_PLUGINS_ENABLED` (that one shows server connectors). It enrols no route: every download runs on the person's computer after they confirm it, and a plugin's hooks and servers still wait for the person's approval. Turning it off hides these sources and refuses them in Desktop; plugins already installed keep working. |
| `TOMVERSE_DESKTOP_MANAGED_CODE_ENABLED` | Shows Desktop's Execution and limits section "Cloud and managed credits" (`desktopManagedCode` capability): where Code can run, and reserving, keeping alive and releasing managed Code credits. Requires the account settings session and `CODE_MANAGED_EXECUTION_ENABLED`. It is a display switch: Desktop reaches `/api/code/managed` with the account settings session as a web page does, and no bearer route is enrolled. A reservation holds the person's credits until released; no model is called. See [desktop-cloud-execution.md](desktop-cloud-execution.md). |
| `TOMVERSE_DESKTOP_CODE_SESSION_ENABLED` | Lets Desktop Code run on the signed-in Desktop session with no Code key (`desktopCodeSession` capability, named only while `EXTERNAL_API_ENABLED` is on and the account is on `EXTERNAL_API_ALLOWED_USER_IDS`). Requires Desktop authentication and migration `20261128110000_external_api_desktop_session`. Desktop asks `POST /api/auth/desktop/code-token` for a short Code token with its session token, and its Code runtimes send only that token, with the Desktop origin, on the agent engine's five coding API calls (`docs/policy/external-api.md` section 11.2). Charges, plan (Pro and above), concurrency and receipts are the coding API's as with a key; no price changes. Off: Desktop keeps the Code key step and a session token is refused on those calls. Desktop builds that predate it keep using Code keys either way. |
| `TOMVERSE_DESKTOP_CLOUD_EXECUTION_ENABLED` | Enables Desktop cloud Code tasks on a runner service (`desktopCloudExecution` capability, `/api/code/cloud`). Requires the account settings session, `CODE_MANAGED_EXECUTION_ENABLED`, `CODE_CLOUD_RUNNER_SECRET` (32+ characters, the same value on the runner), migration `20261128080000_desktop_cloud_execution`, and a deployed runner (`services/code-runner`). No bearer route is enrolled: Desktop uses the account settings session; the runner route is bearer-only with the runner secret. Model calls are reserved and settled on the managed Code path; runner time is not charged. See [desktop-cloud-execution.md](desktop-cloud-execution.md). |

Verify the deployed commit and migration in Test. With the two login flags off, an originless `POST /api/auth/desktop/email` with `{}` returns HTTP 503 and `NOT_AVAILABLE`. With both flags on and the native keyring ready, the same invalid request reaches validation and returns HTTP 400 without sending mail. Requests with cookies or an `Origin` header must be refused, and `/auth/desktop/email-proof` must load with the configured Turnstile site key.

After approval to activate in production, enable the two login flags and repeat the route checks on `tomverse.app`. The Windows 0.1.123 portable uses that origin. With an approved test account, request a code once, enter the received six digits in the Desktop window, confirm the workspace opens, and sign out. Exercise the provider buttons against the configured Apple, Google, and Microsoft accounts when verifying provider login.

Turn off the email flag to stop new email sign-ins. Turn off the Desktop auth flag if the Desktop session routes must also be disabled. Keep the additive device-platform migration in place so existing Desktop device records remain valid.
