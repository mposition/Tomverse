# 외부 assistant package 가져오기 staging 검증 실행 기록

`../assistant-package-import-staging-checklist.md`는 항목만 가진 template입니다.
실행 결과는 여기에 **실행 1회 = 파일 1개**로 남습니다.

규칙은 외부 import·이미지 생성·assistant profile·knowledge·첨부 기록과
같습니다. 여섯 번째로 같은 규칙을 적는 이유도 같습니다 — 이 구조가 만들어진
계기가 **문서 하나가 낡은 채로 공식적으로 보였던 일**이기 때문입니다.

## 파일 이름

```
YYYY-MM-DD__<40자리 deploy SHA>.md
```

전체 SHA를 씁니다. 축약 SHA는 시간이 지나면 충돌할 수 있고, 무엇보다 어느
커밋인지 확인하려면 저장소를 뒤져야 합니다.

## 규칙

1. **기록은 덮어쓰지 않습니다.** 재검증은 새 파일입니다.
2. **비어 있던 항목을 나중에 통과로 채우지 않습니다.** 실행하지 않은 항목은
   `미기록`이며, 그것이 사실입니다.
3. **한 기록은 자기가 실행된 template revision을 적습니다.**
4. **동결된 기록은 digest로 보호합니다.** `frozen: true`인 기록은
   `npm run check:staging-verification-records`가 본문 digest를 대조합니다.
5. **실행·판정·서명은 사람이 합니다.** 실행은 사람이 하고, 통과·조건부·실패의
   **판정**과 **서명**은 사람만 씁니다. 그 둘은 에이전트가 비워 둡니다.

   **관측을 옮겨 적는 것은 에이전트가 합니다.** 사람이 실행하며 보고한 것 —
   무엇이 나왔고 어떤 오류 코드였고 몇 크레딧을 썼는지 — 을 항목·증거·크레딧
   칸에 채워 초안을 만듭니다. 경계는 **관측과 판정**입니다. "거절 코드가
   `ASSISTANT_PACKAGE_UNSAFE_ENTRY`로 떴다"는 관측이고, "그러므로 이 회차는
   통과다"는 판정입니다. 에이전트가 지어낸 관측을 적는 것은 어느 쪽에서도
   허용되지 않으며, 초안은 그것이 초안임을 문서 안에서 밝히고 실행자가 각 줄을
   확인한 뒤 commit 합니다.

## 이 기능에만 있는 규칙

6. **package 내용과 자격증명 문자열을 기록에 넣지 않습니다.** 이 회차는
   자격증명이 심어진 package를 일부러 씁니다. 그 값을 "증거"로 기록에 옮겨
   적으면, 유출을 검증하는 문서가 유출 경로가 됩니다. 적는 것은 **규칙 id와
   개수**입니다 — "`aws-access-key-id` 포함 4건 발견, 원문은 화면에 없었음".

   §C-6이 서버 로그를 직접 열어 확인하라고 하는 항목인데, **거기서 본 것도
   같은 규칙으로 적습니다.** "로그에 없음"이 관측이고, 없다는 것을 보이려고
   있는 것을 옮겨 적을 필요는 없습니다.

7. **시료의 digest를 적습니다.** 실행 전에
   `npm run make:assistant-package-staging-fixtures`를 돌리고, 그 `MANIFEST.md`
   표의 SHA-256을 기록의 시료 표에 옮깁니다. 같은 이름의 다른 바이트로 실행된
   회차와 구분되지 않으면, 나중에 "무엇을 판정한 것인가"에 답할 수 없습니다.

   **manifest의 `생성 시점 관측`이 기대와 다르면 검증을 시작하기 전에
   보고합니다.** 정답지가 낡았거나 코드가 퇴행한 것이고, 어느 쪽이든 그
   상태로 실행한 회차는 무엇을 측정한 것인지 알 수 없습니다.

8. **정리 의무에 R2가 포함되고, 같은 회차 안에서 끝납니다.** 이 회차는
   staging의 R2에 object를 만듭니다. 행을 지우면 bytes는 **다음 정각
   sweep**(:00 · :15 · :30 · :45)에 사라지므로, 삭제 시각과 그 다음 정각 run
   이후의 관측 시각을 함께 적으면 회차 안에서 닫힙니다.

   **취소한 import의 staging 파일도 여기에 포함됩니다.** §E는 취소를 일부러
   실행하므로, 취소가 지웠어야 할 것이 실제로 사라졌는지도 정리 표에
   적힙니다 — 그것이 §E-3·E-4의 사후 증거이기도 합니다.

## 새 실행을 시작할 때

기록은 손으로 복사하지 말고 생성합니다.

```
npm run new:staging-verification-record -- --feature assistant-package-import --sha <staging에 실제 배포된 40자리 SHA>
```

`--preview`를 붙이면 파일을 쓰지 않고 출력만 합니다. 이미 있는 파일은
덮어쓰지 않습니다.

SHA는 git에서 읽지 않고 반드시 인자로 받습니다. 중요한 것은 staging이
**실제로 서빙하고 있는** 커밋이고, 이 기계는 그것을 알 방법이 없습니다.
`GET /api/build-info`가 그 값을 돌려줍니다.

## SHA를 production과 대조할 때

**main으로 가는 릴리스는 squash됩니다.** 그래서 staging에서 검증한 RC SHA는
production 이력에 나타나지 않고, 앞으로도 나타나지 않습니다.

대조는 SHA가 아니라 **내용**으로 합니다.

```
git diff <staging sha> <production sha> -- 'lib/assistantPackage*' \
    'lib/assistantProfileImport*' 'app/api/assistant-profiles/imports/**' \
    'components/assistants/import/**'
```

비어 있으면 두 배포의 가져오기 표면이 같다는 뜻이고, 그 결과를 기록의 실행
환경표에 적습니다.

## 이 회차에 유료 turn이 거의 없는 이유

가져오기는 **모델을 부르지 않습니다.** package를 읽고, 파일을 저장하고,
revision을 게시할 뿐입니다. 크레딧이 드는 것은 가져온 assistant로 실제 대화를
해 보는 §H 두 턴뿐이고, 그것은 차단 항목이 아닙니다.

즉 **차단 항목 30개를 전부 실행해도 0크레딧**입니다. 이 회차를 미룰 비용상의
이유는 없습니다.
