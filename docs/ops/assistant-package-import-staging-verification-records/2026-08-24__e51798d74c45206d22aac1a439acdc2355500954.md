## flag 조작 기록

1회차와 같은 이유로 flag는 **SQL로** 켜고 끕니다 — 이 키에는 애플리케이션
writer도 Admin 콘솔 제어도 없고, 그 구현은
`docs/policy/assistant-package-import.md` §12.2.1이 production 활성화의 별도
차단 조건으로 두고 있습니다. 감사 로그가 생기지 않으므로 그 자리를 이 표가
대신합니다.

| # | 실행자 | UTC 시각 | 실행 SQL | 변경 전 | 변경 후 | `updatedAt` | 배포 SHA |
|---|---|---|---|---|---|---|---|
| 1 | | | `UPDATE "AppSetting" SET value='true'` on `feature.assistantPackageImportEnabled` | `false` | `true` | | `e51798d74c45206d22aac1a439acdc2355500954` |
| 2 | | | `UPDATE ... SET value='false'` (원상복구) | `true` | `false` | | `e51798d74c45206d22aac1a439acdc2355500954` |

**두 조작 모두 실행자·UTC 시각·`updatedAt`이 비어 있습니다.** 실행자가 그때 적지 않았고, 나중에 채우면 관측이 아니라 사후 기입입니다(기록 README 2번). flag가 회차 종료 시점에 `false`로 돌아간 것은 실행자가 확인했습니다.

마지막에 flag가 회차 시작 시점 값(`false`)으로 돌아갔는지 확인하고 적습니다.

## 정리 의무

이 회차는 staging 계정에 profile·knowledge 행을 남기고, **R2 object도
남깁니다.** 취소한 import가 지웠어야 할 것이 실제로 사라졌는지도 여기에
적힙니다 — 그것이 §E-3·E-4의 사후 증거입니다.

| 항목 | 값 |
|---|---|
| 취소한 import의 파일이 사라진 것을 확인 (UTC) | 취소는 실행했습니다(실행자 보고). 취소 후의 행 수를 따로 세지는 않았습니다 — 그 계약은 1회차의 §E-3·§E-4가 행 수준으로 확인했고, 이 회차가 본 것은 §E-1뿐입니다 |
| staging profile·knowledge 삭제 (UTC) | **미수행** |
| 그다음 정각 sweep 이후 bytes 확인 (UTC) | **미수행** |
| 로컬 `.tmp/` 시료 정리 (UTC) / 확인자 | **미수행** |
| `feature.assistantPackageImportEnabled` 되돌리기 | 완료 — `false` (실행자 확인) |

**정리는 1회차와 함께 남아 있습니다.** 두 회차가 같은 staging 계정에 행과 R2
객체를 남겼고, 어느 쪽도 아직 지우지 않았습니다. 나중에 채우면 사후 기입이
되므로 미수행이라고 적습니다.
