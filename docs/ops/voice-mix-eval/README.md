# VOICE-MIX-01 — 한국어·영어 혼용 음성 입력 평가 절차

- 상태: **준비 완료, 실행 전.** 이 문서와 대본·정답지·채점기는 유료 전사 호출
  없이 만들었습니다. 관측 결과는 아직 없습니다.
- 정책: `docs/policy/voice-input.md` §11(보존·제3자 전송), §12(언어를 고정하지 않음,
  transcript를 고치지 않음)를 바꾸지 않습니다.
- 채점기: `lib/voiceMixEvalCore.ts`, 실행 `npm run score:voice-mix-eval`,
  테스트 `tests/voiceMixEvalCore.test.mjs`.
- 대본·정답지: `docs/ops/voice-mix-eval/corpus.v1.json`.

## 1. 무엇을 판별하는가

같은 녹음에서 **현재 모델에 짧은 용어 힌트를 주면 혼용 발화가 나아지는가, 그리고
그 대가로 무엇이 나빠지는가**입니다. 모델 교체는 이 평가의 첫 질문이 아닙니다.

측정은 하나의 인식률로 합치지 않습니다. 고치는 방법이 서로 다르기 때문입니다.

대본과 transcript는 같은 단위열로 읽습니다. 한글 음절 하나, 라틴·숫자 단어 하나가
각각 단위이고, 둘을 **순서를 지키는 정렬 한 번**으로 맞춥니다. 위치가 필요한 측정은
모두 그 정렬에서 읽습니다. 언어별로 따로 떼어 비교하면 두 절을 거꾸로 말해도 만점이
나오기 때문입니다.

| 측정 | 무엇을 셈하는가 | 분모 |
| --- | --- | --- |
| 한국어 문자 오류율 | 정렬에서 한글 단위에 걸린 치환·삭제·삽입 | 대본 한글 음절 합계 (corpus 비율) |
| 영어 단어 오류율 | 같은 정렬에서 라틴·숫자 단위에 걸린 오류 | 대본 영어 단어 합계 (corpus 비율) |
| 핵심 용어 유지 | Tomverse·API·staging 같은 용어가 허용 표기로 남았는가 | 용어 수 |
| 의미 유지 | "배포하지 마세요" 같은 부정·지시 표현이 남았는가 (어휘 대리 지표이지 의미 판정이 아님) | 의미 항목 수 |
| 숫자 순서 유지 | "삼십 → 육십"의 순서가 뒤집히지 않았는가 | 숫자가 둘 이상인 transcript 수 |
| 누락 구간 | 언어 전환 구간에서 정렬로 맞은 단위가 **절반 미만**인가 (정확히 절반은 누락 아님) | 한국어·영어 구간 수 각각 |
| 번역 의심 | 누락된 영어 구간 자리에 그 구간 단어 수 이상의 한글이 들어왔는가. 그 한글이 대본이 허용한 음차 표기(예: 스테이징)이면 번역이 아니라 음차로 따로 셉니다 | 누락된 영어 구간 수 |
| 힌트 삽입 | 힌트 용어가 대본에 없는데 transcript에 나왔는가 | transcript 수·용어 수 |

- **경계:** 허용 표기의 라틴·숫자 끝은 단어 경계에 있어야 합니다. "30"은 "300"에,
  "API"는 "rapid"에 맞지 않습니다. 한글은 띄어쓰기·조사가 달라지므로 공백 없이 비교합니다
  (한글 표기가 더 긴 한글 단어 안에서 맞을 수 있다는 한계가 있어 corpus는 구별되는 표기를 씁니다).
- **표기 충실도와 용어 유지는 따로:** "스테이징"은 staging 용어를 지킨 것으로 세고, 동시에
  대본 철자 기준 영어 단어 오류로도 셉니다. 둘 다 사실이며 따로 보고합니다.
- 기준(단위, 누락 50%, 번역 규칙)은 결과를 보기 전에 코드로 고정했습니다
  (`voice-mix-scoring-v3`). v1은 경계 없는 일치·순서 무시·실행 무결성 부재로, v2는 음차를 번역으로
  세는 문제로 Codex 검토에서 반려되어 둘 다 결과 없이 대체했습니다. 결과를 본 뒤 바꾸면 질문이 바뀐 것이므로 버전을 올리고
  이 문서에 이유를 적습니다.

## 2. 대본의 분리

- **dev 5개:** 작업 목록에 적힌 대본 후보입니다. 힌트를 만드는 동안 들어 봐도 됩니다.
- **holdout 10개:** 비교 판정에만 씁니다. 힌트를 고정한 뒤에만 녹음·전사하고,
  그 결과를 보고 힌트를 다시 고치지 않습니다.
- **힌트는 dev에서만 가져옵니다.** `hintVocabulary`의 모든 용어는 dev 대본에 있어야 하고,
  hinted arm이 보낼 문장 `hintPrompt`도 corpus에 글자 그대로 고정합니다. 채점기의 corpus
  검사가 둘 다 강제합니다. 모든 요청이 같은 문장을 받으며, 각 대본의 정답을 그 요청의
  힌트로 넣지 않습니다.
- **두 층으로 나눠 보고합니다.** 힌트 용어가 대본에 나오는 `hint-target`(holdout-01·09·10)과
  나오지 않는 `hint-absent`(나머지 7개)입니다. 앞은 힌트가 용어를 돕는지, 뒤는 힌트가
  **없는 말을 끼워 넣는지**를 봅니다. 어느 대본이 어느 층인지는 채점기가 계산하며 이 목록은
  설명용입니다.

## 3. 비교 설계 — 승인 요청 사항

| 항목 | 제안 |
| --- | --- |
| 모델 | 현재 운영 설정 모델 1개. `gpt-4o-mini-transcribe`가 코드 기본값이지만 실제 환경변수는 실행 전에 확인 |
| arm | A: 힌트 없음(현재 동작) · B: `prompt`에 `hintVocabulary`를 한 문장으로 전달 |
| 녹음 | holdout 10개 × 화자 2명 × 조건 2개(조용한 실내, 약한 소음) = 40개 녹음 |
| 반복 | 각 녹음을 arm마다 3회 전사 (같은 녹음을 다시 보내므로 녹음은 늘지 않음) |
| 호출 수 | 40 × 2 arm × 3 = **240회** (+ dev 파이프라인 확인 5 × 2 = 10회) |
| 예상 비용 | 근거: `docs/policy/voice-input.md` §6.1.3의 청구 관측 — `gpt-4o-mini-transcribe-2025-12-15`, 3회, measured_clip 합계 35.249초, 청구 US$0.001616(오디오 초당 약 US$0.000046). 대본 한 번 읽기를 6초로 잡으면 250회 × 6초 ≈ **US$0.07**, 호출당 비용을 그대로 쓰면 250회 × US$0.000539 ≈ **US$0.13**. 비용은 오디오 길이에 비례하므로 실제 녹음 길이로 다시 계산합니다. 예산 상한 **US$1.00** 제안 |
| 판별하는 것 | hint-target 층에서 B가 A보다 핵심 용어·의미·숫자 순서를 더 지키는지, 그리고 두 층 모두에서 힌트 삽입·한국어 문자 오류율·영어 단어 오류율이 나빠지지 않는지 |
| 실행 목록 | 실행 전에 manifest를 기록에 고정합니다: corpus 버전과 파일 SHA-256(`--check-corpus`가 출력), 채점 버전, holdout 전체 id, `speaker/condition` take(화자 2명 이상 × 조건 2개 이상, 모든 조합), 반복 3회, arm 두 개(`no-hint`는 prompt 없음, `hint`는 corpus의 `hintPrompt` 그대로, 두 arm 같은 모델). 채점기는 이 절차에서 벗어난 manifest와, manifest와 정확히 같지 않은 실행(빠짐·중복·미등록·한쪽 arm에만 있는 녹음)을 거절합니다 |

`gpt-transcribe`(`keywords`·`languages` 지원)는 이 비교의 대상이 아닙니다. 가격
등록부 후보가 다르므로, 위 결과를 보고 필요할 때 별도로 승인받습니다.

## 4. 사람만 할 수 있는 것

AGENTS.md의 기준에 따라 이 넷만 남깁니다.

1. **실제 발화 녹음** — 합성 음성은 억양·마이크·혼용 발화를 대신하지 못합니다
   (파이프라인 확인용으로만 씁니다).
2. **유료 호출 승인** — 위 §3의 호출 수와 예산.
3. **실제 운영 모델 확인** — `VOICE_TRANSCRIPTION_MODEL`을 읽을 권한.
4. **판정** — 아래 기록의 결론과 서명.

녹음 파일과 transcript는 평가를 위해 명시적으로 만든 것만 씁니다. production
사용자의 녹음·전사문은 수집하지도 로그로 남기지도 않습니다(정책 §11). 평가 녹음의
보관 위치·삭제 시점은 실행 전에 정해 기록에 적습니다.

## 5. 실행 순서 (승인 후)

1. 에이전트가 dev 5개를 합성 음성으로 만들어 A·B 요청 경로와 채점을 끝까지 한 번
   돌립니다. 이 결과는 파이프라인 확인이며 성능 증거로 인용하지 않습니다.
2. 사람이 holdout 10개를 §3 조건으로 녹음합니다. 파일 이름은
   `<itemId>__<speaker>__<condition>.webm`.
3. 에이전트가 arm·반복별로 전사해 transcripts 파일을 arm마다 하나씩 만들고
   (`entries[]`는 `itemId`·`take`(`speaker/condition`)·`repeat`·`transcript`) 두 arm을
   함께 채점합니다.

   실행 위치: 에이전트 작업 환경 또는 로컬 PC의 PowerShell, Tomverse clone 폴더 안. Node 22와
   `npm ci`가 끝나 있어야 합니다. 자격증명이 필요 없고 읽기 전용이며(파일을 읽고 결과만 출력),
   provider를 호출하지 않습니다.

   ```bash
   npm run score:voice-mix-eval -- --manifest runs/manifest.json --transcripts runs/no-hint.json --transcripts runs/hint.json
   ```

   1번의 합성 확인은 manifest 없이 `--pipeline-check`로 dev 대본만 채점하며, 출력에
   증거가 아니라고 표시됩니다.

4. 에이전트가 두 보고서를 나란히 놓은 기록 초안을 만들고, 사람이 판정합니다.

## 6. 판정에서 하지 않는 것

- 개선율을 미리 약속하지 않습니다. 40개 녹음은 방향을 보는 크기이며 전체 사용자에
  대한 일반화가 아닙니다.
- 힌트 삽입이 하나라도 늘었다면 용어 유지가 좋아져도 그대로 출시 근거로 쓰지 않고,
  목록을 줄이는 재설계를 먼저 검토합니다.
- transcript를 일반 LLM으로 몰래 고치는 방식은 비교 대상이 아닙니다(정책 §12).
