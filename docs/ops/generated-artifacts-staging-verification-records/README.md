# AI 생성 파일 staging 검증 실행 기록

`../generated-artifacts-staging-checklist.md`는 항목만 가진 template입니다.
실행 결과는 여기에 **실행 1회 = 파일 1개**로 남습니다.

규칙은 외부 import·이미지 생성·assistant profile 기록과 같습니다. 같은 규칙을
네 번째로 적어 두는 이유는, 이 구조가 만들어진 계기가 **문서 하나가 낡은 채로
공식적으로 보였던 일**이기 때문입니다.

## 파일 이름

```
YYYY-MM-DD__<40자리 deploy SHA>.md
```

전체 SHA를 씁니다. 축약 SHA는 시간이 지나면 충돌할 수 있고, 무엇보다 어느
커밋인지 확인하려면 저장소를 뒤져야 합니다. 날짜가 앞에 오는 것은 목록이
시간순으로 정렬되게 하기 위해서입니다.

## 규칙

1. **기록은 덮어쓰지 않습니다.** 재검증은 새 파일입니다.
2. **비어 있던 항목을 나중에 통과로 채우지 않습니다.** 실행하지 않은 항목은
   `미기록`이며, 그것이 사실입니다.
3. **한 기록은 자기가 실행된 template revision을 적습니다.**
4. **동결된 기록은 digest로 보호합니다.** `frozen: true`인 기록은
   `npm run check:staging-verification-records`가 본문 digest를 대조합니다.
5. **실행·판정·서명은 사람이 합니다.** 에이전트는 기록 파일의 뼈대를 만들 수
   있지만 결과·서명란을 채울 수 없습니다.

## 이 기능에만 있는 규칙

6. **§A는 에이전트가 채울 수 있습니다.** 무인증 HTTP 응답이 전부이고 판단이
   들어가지 않기 때문입니다. 나머지 구획은 사람이 채웁니다 — §C의 "Excel이
   경고 없이 열었다"는 자동화가 대신 말할 수 있는 문장이 아닙니다.
7. **§C와 §K-2는 파서가 아니라 뷰어로 판정합니다.** 로컬 CI가 이미 파서로
   읽었으므로, 여기서 파서를 다시 돌리면 아무것도 새로 알아내지 못합니다.
   특히 PDF의 한글은 임베드가 잘못돼도 **파서 검증을 통과**하고 화면에서만
   빈칸으로 드러납니다.
8. **파일 내용을 기록에 붙여 넣지 않습니다.** 관측만 적습니다 — "3개 시트,
   헤더 4열, 수식 0개"처럼. 다운로드한 파일 자체는 저장소가 아니라 제한된
   운영 저장소에 두고 참조만 남깁니다.
9. **artifact id를 기록에 적지 않습니다.** §F·§G의 증거는 "다른 계정에서 404,
   본문에 파일명 없음"이지 id가 아닙니다.

## 새 실행을 시작할 때

기록은 손으로 복사하지 말고 생성합니다.

```
npm run new:staging-verification-record -- --feature generated-artifacts --sha <staging에 실제 배포된 40자리 SHA>
```

체크리스트의 전 구획을 읽어 항목마다 한 행씩 펼친 빈 기록을 만듭니다.
`--preview`를 붙이면 파일을 쓰지 않고 출력만 합니다. 이미 있는 파일은
덮어쓰지 않습니다 — 기록은 한 실행의 기록이고, 두 번째 실행은 두 번째
파일입니다.
