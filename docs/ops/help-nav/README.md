## 정답지

- dev 22개, holdout 21개. 한국어 중심에 영어 포함. 사용자에게서 모은 질문이 아니라 이 검사용으로 쓴 합성 질문입니다.
- 한 사례에 기대값 하나: 의도 하나(`expect`), 되물어야 하는 경우(`clarify`, 정말 두 의도에 다 맞을 때만), 지원하지 않는 요청(`unsupported`). 되묻기와 거절에는 이유를 붙입니다.
- 매칭 규칙을 만들 때는 dev만 보고, holdout은 판정에만 씁니다. holdout은 제품 용어를 덜 쓰고, 비슷하지만 없는 기능(메모장)·관리자 경로·대화 본문을 읽어 달라는 요청처럼 거절해야 하는 경우를 따로 담았습니다.
- 구매 요청(크레딧 충전해 주세요)은 되묻기가 아니라 `credits-and-plan` 안내입니다. 어디서 사는지 알려 주고 사지는 않습니다.

## 매처 v1 결과 (2026-09-17)

규칙은 dev만 보고 만들었고, holdout은 규칙을 고정한 뒤 한 번 채점했습니다. holdout 결과를 보고 규칙을
고치지 않았습니다 — 고치면 그 사례는 더 이상 holdout이 아닙니다.

| split | 통과 | 거절해야 할 질문을 의도로 답함 |
| --- | --- | --- |
| dev | 22/22 | 0 |
| holdout | 12/21 | 1 (h20) |

독립 검토(Codex) 뒤 거절 규칙을 보강했습니다 — 첨부·Memory·가져온 대화·초안 읽기 요청 거절, `sign-in`처럼 하이픈이 든 표기와 "비밀번호를 잊었어요", 다른 사람과 공유하는 방법 질문의 과잉 거절 해소, 범위가 좁은 데이터 삭제 질문의 되묻기 제외. 근거는 검토자가 든 예시이며 holdout 문항이 아닙니다. 3차 검토 뒤에는 표현을 하나씩 막는 대신 기본값을 바꿨습니다: 비밀번호 질문은 대화 잠금을 분명히 말하고 로그인·계정을 말하지 않을 때만 답하고, 다른 사람이 언급된 절은 공유 방법 질문일 때만 답하며, 거절 판정은 쉼표·and·그리고로 나눈 절마다 합니다. 보강 후 재채점 결과는 위 표와 같습니다(dev 22/22, holdout 12/21, 같은 9건). 안전 실패 집계는 거절해야 할 질문을 의도로 답한 경우뿐 아니라 되묻기로 제시한 경우도 셉니다.

holdout 실패 9건 중 8건은 `unsupported`로 떨어졌습니다(h03·h04·h06·h07·h08·h12는 의도가 있었고,
h14·h19는 되물어야 했음). 사용자에게는 도움말 센터와 문의 창이 제시되므로 틀린 곳으로 보내지는 않지만,
답할 수 있는 질문을 답하지 못한 것입니다. 나머지 1건(h20)은 거절해야 할 질문을 `manage-memory`로
답했습니다. 목적지는 설정 링크뿐이라 읽기·변경은 일어나지 않지만, 화면에 붙이기 전에 결정이 필요합니다.

- 제품 용어를 덜 쓰는 질문에서 키워드 매칭의 한계가 드러났습니다. 다음 선택지: 동의어를 늘리고 **새
  holdout(v3)** 으로 다시 판정하거나, 모델 없는 검색(예: 의도 설명과의 유사도)을 비교합니다.
- 이 결과는 품질 승인이 아니며, UI 연결 전 판단 자료입니다.
- 거절 규칙은 정규식이라 표현 목록의 한계가 남습니다. 검토 4회 동안 매번 새 우회 표현이 나왔고, 기본값을 거절 쪽으로 옮겨 줄였지만 없앤 것은 아닙니다. 어느 쪽으로 틀려도 결과는 도움말 센터·문의 창 또는 등록된 목적지 링크뿐이며 아무것도 읽거나 바꾸지 않습니다. 화면에 붙이기 전에 이 한계를 받아들일지 결정이 필요합니다.
