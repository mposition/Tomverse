# 음성 입력 staging 검증 실행 기록 (B-6)

`../voice-input-staging-checklist.md`는 항목만 가진 template입니다. 실행 결과는
여기에 **실행 1회 = 파일 1개**로 남습니다.

`docs/policy/voice-input.md` §14의 **B-6이 마지막 차단 사유**입니다. B-1~B-5는
닫혔고, 그중 B-5는 2026-09-10에 통과로 서명됐습니다
(`../voice-provider-data-controls-records/2026-09-10-us-regional-endpoint.md` §14).
**여기서 통과가 나오면 production에서 `feature.voiceInputEnabled`를 켜는 결정만
남습니다.**

## 파일 이름

```
YYYY-MM-DD__<40자리 deploy SHA>.md
```

전체 SHA를 씁니다. 축약 SHA는 시간이 지나면 충돌할 수 있고, 무엇보다 어느
커밋인지 확인하려면 저장소를 뒤져야 합니다. 날짜가 앞에 오는 것은 목록이
시간순으로 정렬되게 하기 위해서입니다.

**Voice에서는 이 SHA가 특히 잘 어긋납니다.** 2026-09-10 하루에 staging이 다섯 번
움직였고 그중 셋을 기록 PR이 움직였습니다. **merge SHA를 옮겨 적지 말고 실행
시점에 `GET /api/build-info`를 읽으십시오** — 그 endpoint는 로그인 없이 열립니다.

## 규칙

1. **기록은 덮어쓰지 않습니다.** 재검증은 새 파일입니다. 과거 실행이 무엇을
   보고 무엇을 보지 않았는지가 그 기록의 가치이고, 고쳐 쓰면 사라집니다.
2. **비어 있던 항목을 나중에 통과로 채우지 않습니다.** 실행하지 않은 항목은
   `미기록`이며, 그것이 사실입니다.
3. **한 기록은 자기가 실행된 template revision을 적습니다.** 그래야 나중에
   추가된 항목을 "그때는 없던 항목"으로 읽을 수 있습니다.
4. **동결된 기록은 digest로 보호합니다.** `frozen: true`인 기록은
   `npm run check:staging-verification-records`가 본문 digest를 대조합니다.
   내용을 고치면 digest가 어긋나 검사가 실패하고, digest를 다시 계산해 넣는
   것은 diff에 드러나는 의도적 행위입니다. 자물쇠가 아니라 기록입니다.
5. **실행·판정·서명은 사람이 합니다.** 실행은 사람이 하고, 통과·조건부·실패의
   **판정**과 **서명**은 사람만 씁니다. 그 둘은 에이전트가 비워 둡니다.

   **관측을 옮겨 적는 것은 에이전트가 합니다.** 실행자가 보고한 것 — 무엇이
   나왔고 어떤 오류 코드였고 무엇을 말했고 무엇이 찍혔는지 — 을 항목·증거 칸에
   채워 초안을 만듭니다. 본 것을 다시 타이핑하게 만드는 것은 준비를 떠넘기는
   일이고, 1인 조직에서 그 비용이 기록을 미루게 만듭니다.

   경계는 **관측과 판정**입니다. "표시등이 켜져 있었다"는 관측이고, "그러므로
   이 회차는 통과다"는 판정입니다. **지어낸 관측은 어느 쪽에서도 허용되지
   않습니다.**

## Voice에만 있는 것 셋

**첫째, D 구획은 사람이 할 일이 없습니다.** 체크리스트는 로그를 "꺼내 주기만
합니다"라고 적었지만, 에이전트가 Railway에서 직접 읽을 수 있습니다. 실행 시각만
알려 주면 `event: "voice_transcription"` 라인을 꺼내 `docs/policy/voice-input.md` §11.2의 필드 목록과
대조합니다.

**둘째, C 구획은 말한 문장과 나온 문장을 둘 다 적습니다.** "잘 나왔다"는 관측이
아닙니다. 인식 품질 판정은 사람만 할 수 있고, 그 판정의 근거가 그 두 문장입니다.

**셋째, 유료입니다.** 항목당 1회, 약 10회, 예상 US$0.01 미만. **보장된 상한이
아닙니다** — output 토큰은 발화 밀도에 따라 달라집니다. 분당 추정 비용이나 공표
가격표로 상한을 계산하지 않습니다(`docs/policy/voice-input.md` §6.1.3).

## 무엇이 차단이고 무엇이 아닌가

체크리스트의 "차단 / 비차단" 구획이 정하며, 기준은 **틀렸을 때 되돌릴 수
없는가**입니다.

**차단** — E(kill switch, 무료), A-1·A-2의 마이크 표시등과 취소, C의 "자동
전송되지 않음", F의 회귀 넷.

**비차단** — B-1(Safari MP4 길이 선언), B-2(Firefox 협상), A-3(통화 경합),
C의 인식 품질.

**가장 중요한 차단 항목인 E가 무료입니다.** 범위를 줄일 때 E와 F를 먼저 하고
유료 구획을 나중에 두는 것이 가능하며, 건너뛴 구획은 `미기록`으로 남기고
판정란에 **무엇을 왜 건너뛰었는지** 적습니다.

## 실행 전에 한 번 더 볼 것

B-5는 통과했지만 **잔여 위험이 수용된 채로 열려 있습니다.** 그중 하나만
사용자에게 보이는 문장에 걸립니다.

> **7-1** — 지금 고지는 "이전 국가: 미국"이라고 말하고, 그 근거는 수령 법인
> `OpenAI OpCo, LLC`의 소재지입니다. **계약 원문과 대조된 것은 명칭뿐입니다.**

**production 공개는 staging보다 그 문장이 닿는 범위가 넓습니다.** 그래서
체크리스트의 사전 조건에 이 항목의 재확인이 들어 있습니다.

## 새 실행을 시작할 때

기록은 손으로 복사하지 말고 생성합니다.

```
npm run new:staging-verification-record -- --feature voice-input --sha <staging에 실제 배포된 40자리 SHA>
```

체크리스트의 전 구획을 읽어 항목마다 한 행씩 펼친 빈 기록을 만듭니다.
`--preview`를 붙이면 파일을 쓰지 않고 출력만 합니다. 이미 있는 파일은
덮어쓰지 않습니다.

**손으로 항목을 옮기지 않습니다.** 빠진 행은 아무도 실행하지 않은 구획과
똑같이 보입니다.

SHA는 git에서 읽지 않고 반드시 인자로 받습니다. 중요한 것은 staging이
**실제로 서빙하고 있는** 커밋입니다.

## 실행 순서

1. `GET /api/build-info`로 staging이 서빙 중인 40자리 SHA를 읽습니다.
2. 그 SHA로 기록을 생성합니다. **커밋하지 않은 상태로 둡니다.**
3. 사람이 항목별로 실행하고 결과·증거를 보고합니다. 에이전트가 초안에
   옮겨 적습니다.
4. 필수 항목에 `미기록`이 남아 있으면 전체 결과를 `통과`로 서명하지
   않습니다.
5. 실행자·승인자가 서명합니다.
6. 최종 본문으로 digest를 계산합니다.
7. `frozen: true`와 digest를 적습니다.
8. `npm run check:staging-verification-records`가 통과한 뒤에 커밋합니다.

```
node scripts/check-staging-verification-records.mjs --digest <파일>
```
