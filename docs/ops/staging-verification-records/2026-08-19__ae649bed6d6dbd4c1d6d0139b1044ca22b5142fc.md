정식 실행이 통과해도 그것은 **이 코드와 migration 조합이 올바르게 동작한다**는
근거이지, production이 그 상태라는 증명이 아닙니다. 활성화 전에 production에서
따로 확인하고, 그 결과는 `environment: production`인 **별도 기록**에 적습니다.

그리고 동결한 뒤 다음 중 하나가 달라지면 이 기록은 새 대상을 덮지 못합니다 —
활성화 대상 SHA, 적용 migration 집합, import·parser·wizard 관련 코드, 검증
결과에 영향을 주는 flag·런타임 설정, 실제 배포 artifact.

### 활성화 판단 — 이 기록을 근거로 삼는다는 결정

체크리스트는 정식 실행을 **예정된 production 활성화 대상 SHA 위에서** 요구하고,
탐색 실행을 활성화 승인 근거로 인용하지 말라고 한다. 이 회차는 탐색 실행이다.
그럼에도 이 결과를 근거로 `feature.externalConversationImportEnabled`를 켜기로
한다. 그 결정을 여기 적는 이유는, 나중에 문제가 생겼을 때 **무엇을 알고 열었는지**가
남아야 하기 때문이다. 절차를 지켰다고 적는 것보다 지키지 않은 지점을 적는 쪽이
기록으로서 쓸모가 있다.

판단의 기준은 되돌릴 수 있는지였다. 잘못된 문구, 안 그려지는 지표, 어긋난
레이아웃은 고치면 그 시점부터 고쳐진다. 뷰어가 남의 export에 든 스크립트를
실행하거나, flag off가 API를 막지 못하거나, 저장 계약이 깨져 선택하지 않은 대화가
저장되는 것은 일어난 뒤에 되돌아가지 않는다. 그래서 A(fail-closed 4/4),
C·C2의 저장·seal 계약, D-1(XSS)을 먼저 확인하고 나머지를 남겼다.

남긴 것과 그 대가:

- **Gemini(H2)** — Gemini는 이 flag와 함께 서비스한다(운영 결정). 이 회차에서 확인한
  것은 안내 카드 한 건이지만, 나머지는 2026-08-18 회차(`79d967f`)가 실제 Takeout
  ZIP으로 확인했고 **그 결과가 이 빌드에 이어진다** — `79d967f..ae649be`의 import
  관련 변경이 문서 2건뿐이고 adapter·pipeline·limits·digest·컴포넌트·API 라우트에
  코드 변경이 없기 때문이다. 각 H2 항목에 그 근거를 적어 두었다.

  코드 무변경이 재실행을 대신하지는 않는다. 두 회차의 데이터베이스 상태·계정·런타임
  설정이 같다는 보장은 없고, 어제 회차가 덮지 않은 것(아카이브 미업로드, ko/en 두
  계정)은 오늘도 덮이지 않은 채다. 그러나 "같은 코드가 같은 파일을 같은 결과로
  파싱했다"는 사실은 남으며, Gemini를 검증 없이 여는 것과는 다른 상태다.
- **D-2 IDOR · D-3 로그 유출** — 두 번째 계정과 로그 열람이 필요해 실행하지 않았다.
  소유권이 서버에서 판정된다는 것은 코드로 확인했으나, 존재 여부가 새지 않는지는
  코드만으로 대체되지 않는다.
- **E(quota) · F 대부분** — 50 MB를 채우는 비용과 기기·locale 준비가 필요하다.
  실패해도 사용자가 막히거나 불편한 수준이며 데이터를 잃지 않는다.
- **사전 조건 전체** — migration 선후, 검증 계정 준비, 정리 담당자 지정을 기록하지
  않았다.

이 결정은 production에서 따로 확인해야 할 것을 없애지 않는다. 정식 실행이
필요해지면 그때의 활성화 대상 SHA에서 A~H/H2 전체를 다시 실행한다.

### 발견-A — `notImportableBadge`가 쓰이지 않는 문자열이다

체크리스트가 1,000,000 code point 초과 대화를 "**가져올 수 없음**으로 표시"라고
적고 있고 `locales/ko.ts:1128`에 `notImportableBadge: "가져올 수 없음"`이 7개
locale 모두 번역까지 들어간 채 정의되어 있는데, 이 키를 **코드 어디에서도 쓰지
않는다**.

```
grep -rn "notImportableBadge" --include=*.tsx --include=*.ts . | grep -v locales/
→ 결과 없음
```

화면은 상단 배너·행 경고·`disabled` 체크박스 세 층으로 같은 사실을 전달하므로
해당 항목은 pass로 두었다. 다만 배지를 붙이려다 빠진 것인지 문구를 폐기한
것인지는 코드만 봐서 구분되지 않는다. 문자열을 지우든 배지를 붙이든 한쪽으로
정리하고, 체크리스트 문구도 실제 화면과 맞춘다.

### 발견-B — 감사 로그 action 이름이 바뀐 것을 가리키지 않는다

`app/api/admin/app-settings/route.ts`가 platform defaults와 feature flag 전체를
한 PUT으로 처리하면서 항상 같은 두 줄만 남긴다.

```
:107  action: "app_settings.update_started"
:128  action: "app_settings.guest_default_model.updated"
```

external import flag만 켠 변경도 `app_settings.guest_default_model.updated`로
기록된다. "external import가 언제 켜졌나"를 감사 로그에서 찾으려는 사람은
import 관련 action을 검색하다 아무것도 찾지 못하고, 실제 값은 `metadata` 안에만
있다. 목록 화면의 ACTION·SUMMARY 열에는 드러나지 않으므로 상세를 열어야 한다.

게다가 metadata는 요청 body 전체이므로 **한 항목만 봐서는 바뀐 값과 그대로인
값을 구분하지 못한다.** 이 회차의 10:49(on)과 12:06(off) 두 항목은 나머지 7개
필드가 완전히 같고 `externalConversationImportEnabled`만 다르므로 diff를 사람이
재구성할 수는 있다. 다만 그것은 두 항목 사이에 다른 변경이 없었다는 사실을 이미
알고 있을 때만 성립하며, 감사 로그 자체는 그 사실을 보장하지 않는다.

체크리스트 항목의 요구("audit 로그에 app_settings 갱신이 남는다")는 충족되므로
fail이 아니다. flag별 action 또는 before/after diff를 남기는 것이 후속 대상이다.

### 발견-C — 진입점을 숨긴 뒤에도 그 기능을 설명하는 문구가 남는다

flag off 상태의 Data 탭에서 「다른 AI 서비스에서 가져오기」 행은 사라지지만, 그
행을 담고 있던 그룹의 설명은 「가져온 대화와 계정 기억입니다」 그대로이고,
「계정 장기 기억」 행의 설명도 「가져온 대화에서 추출한 기억 후보를 검토하고…」
그대로다.

flag를 한 번도 켠 적 없는 계정에서는 도달할 방법이 없는 기능을 설명하는 문구가
된다. A-3 항목의 요구는 "진입점이 보이지 않는다"이고 진입점 자체는 숨었으므로
pass로 두었으나, 문구를 조건부로 바꿀지 그대로 둘지는 설계 결정이므로 여기서
단정하지 않는다.

### 발견-D — rollback 상태에서 export 버튼이 함께 사라진다

`components/imports/ExternalImportManagement.tsx`의 파일 주석은 "the history
list, delete and export stay reachable so a rollback never strands imported
data (§15)"라고 적고 있다. 실제로 export API에는 flag gate가 없다
(`app/api/imports/external/export/route.ts` 전체에 `assertExternalImportEnabled`
없음). 그러나 UI의 「전체 내려받기」 버튼(:491-506)은 대화 목록 섹션 안에 있고,
그 섹션 전체가 `conversationsState.kind !== "hidden"`으로 감싸여 있다(:480).

```
GET /api/external-conversations  ->  403 (flag gate 있음)
  -> conversationsState = "hidden"
    -> 섹션 미렌더링 -> 그 안의 export 버튼도 사라짐
```

버튼의 가시성이 export의 가용성이 아니라 **대화 목록의 가용성에** 묶여 있다.
데이터가 고립되지는 않는다 — 계정 전체 내려받기(`/api/user/account/export`)에도
flag gate가 없고 Data 탭의 「내 계정 데이터」가 "가져온 기록"을 포함한다고
명시하므로 UI 경로가 남아 있다. 따라서 G-1을 fail로 보지 않고 의도치 않은 결합으로
기록한다. 고치려면 버튼을 대화 목록 상태가 아니라 이력 존재 여부에 묶으면 된다.

### 발견-E — import 지표를 화면에 그리는 곳이 없다

`components/admin/AdminMemoryImportPanel.tsx`는 두 관측 API를 함께 부르지만
memory 쪽만 렌더링한다. `/api/admin/external-imports`의 응답이 닿는 곳은 state
하나와 그 state가 `null`인지 보는 한 줄뿐이다.

```
:163  fetch("/api/admin/external-imports", { cache: "no-store" })
:191  setImports(importData)
:435  {imports === null && ( "The import report is unavailable in this environment" )}
```

provider·parserVersion 분해도, 두 비율도, 세 bucket도, 카운터도 그리는 코드가
없다. 타입조차 `{ windowDays?: number; [key: string]: unknown }`이라 어떤 필드가
있는지 모른다. API가 정상이면 화면에는 아무 흔적도 남지 않는다 — "unavailable"
문구마저 `null`일 때만 나오기 때문이다.

이 파일 상단 주석이 밝힌 존재 이유가 그 반대다.

> `/api/admin/external-imports` since Release A and `/api/admin/memory` since the
> memory metrics landed. **A metric nobody reads is not a metric, so this panel
> is the other half of both.**

memory 쪽만 구현되고 import 쪽은 fetch만 남았다. 이 회차에서 F 지표를 콘솔에서
직접 호출해야 했던 것이 그 증거다.
