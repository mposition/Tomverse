## 이 기록이 덮는 범위

정식 실행이 통과해도 그것은 **이 코드와 migration 조합이 올바르게 동작한다**는
근거이지, production이 그 상태라는 증명이 아닙니다. 활성화 전에 production에서
따로 확인하고, 그 결과는 `environment: production`인 **별도 기록**에 적습니다.

그리고 동결한 뒤 다음 중 하나가 달라지면 이 기록은 새 대상을 덮지 못합니다 —
활성화 대상 SHA, 적용 migration 집합, import·parser·wizard 관련 코드, 검증
결과에 영향을 주는 flag·런타임 설정, 실제 배포 artifact.

| | **HTML 형식으로 내보낸 파일**을 올리면 파일 선택기에서 고를 수 있고, "내 활동을 JSON 형식으로 다시 내보내 주세요"라는 안내가 나온다. 일반 "읽을 수 없음"이 아니다(§6). 진단 라벨은 `html_export_unsupported`. | | | |
| | Gems·예약 작업 파일(`Takeout/Gemini/*.html`)만 담긴 ZIP도 같은 안내로 이어지고, 조용히 "대화 0건"으로 끝나지 않는다. | | | |
| | 활동 기록이 꺼져 있어 대화가 없는 export는 **오류가 아니라 정상 상태**로 구분해 표시된다(§1). | | | |
| | admin 지표에서 이 import가 provider `gemini`로 잡힌다. | | | |
| **H · H2. 분기가 실제로 얼마를 쓰는지** | | | | |
| | preview에 표시된 분기 중복 메시지 수가 실제 값과 **정확히** 일치한다. | | | |
| | 그 숫자가 **선택분이 아니라 export 전체 기준**임을 화면에서 알 수 있다. | | | |
| | 분기 대화를 해제하면 **선택 메시지 수와 예상 저장 bytes가 즉시 줄어든다.** | | | |
| | **어느 대화를 해제해야 하는지 사용자가 식별할 수 있다.** 목록에서 분기끼리 구분되지 않으면, 총량 경고만 있고 손댈 방법이 없는 상태다. | | | |
| | 서버 finalize 뒤 실제 저장량이 선택 화면의 예상량과 맞는다. | | | |

증거는 스크린샷 경로, 로그 발췌 위치, admin 응답 캡처처럼 **다시 확인할 수
있는 것**을 적습니다. 개인 데이터가 있는 자료는 저장소가 아니라 제한된 운영
저장소에 두고 여기에는 참조만 남깁니다.

| 항목 | 값 |
|---|---|

| 후속 티켓 | 미발행 |

### 발견-A — `notImportableBadge`가 쓰이지 않는 문자열이다

체크리스트가 1,000,000 code point 초과 대화를 "**가져올 수 없음**으로 표시"라고
적고 있고 `locales/ko.ts:1128`에 `notImportableBadge: "가져올 수 없음"`이 7개
locale 모두 번역까지 들어간 채 정의되어 있는데, 이 키를 **코드 어디에서도 쓰지
않는다**.

```
grep -rn "notImportableBadge" --include=*.tsx --include=*.ts . | grep -v locales/
→ 결과 없음
```

화면은 상단 배너·행 경고·`disabled` 체크박스 세 층으로 같은 사실을 전달하므로
해당 항목은 pass로 두었다. 다만 배지를 붙이려다 빠진 것인지 문구를 폐기한
것인지는 코드만 봐서 구분되지 않는다. 문자열을 지우든 배지를 붙이든 한쪽으로
정리하고, 체크리스트 문구도 실제 화면과 맞춘다.

### 발견-B — 감사 로그 action 이름이 바뀐 것을 가리키지 않는다

`app/api/admin/app-settings/route.ts`가 platform defaults와 feature flag 전체를
한 PUT으로 처리하면서 항상 같은 두 줄만 남긴다.

```
:107  action: "app_settings.update_started"
:128  action: "app_settings.guest_default_model.updated"
```

external import flag만 켠 변경도 `app_settings.guest_default_model.updated`로
기록된다. "external import가 언제 켜졌나"를 감사 로그에서 찾으려는 사람은
import 관련 action을 검색하다 아무것도 찾지 못하고, 실제 값은 `metadata` 안에만
있다. 목록 화면의 ACTION·SUMMARY 열에는 드러나지 않으므로 상세를 열어야 한다.

게다가 metadata는 요청 body 전체이므로 **바뀐 값과 그대로인 값을 구분하지
못한다.** 같은 payload가 이미 켜져 있던 flag를 다시 저장한 경우와 방금 켠 경우를
같은 모양으로 남긴다.

체크리스트 항목의 요구("audit 로그에 app_settings 갱신이 남는다")는 충족되므로
fail이 아니다. flag별 action 또는 before/after diff를 남기는 것이 후속 대상이다.
