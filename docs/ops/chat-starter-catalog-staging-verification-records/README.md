# Chat 시작 카탈로그 staging 검증 실행 기록

`../chat-starter-catalog-staging-checklist.md`는 항목만 가진 template입니다.
실행 결과는 여기에 **실행 1회 = 파일 1개**로 남습니다.

여기서 통과가 나오면 production에서 `feature.chatStarterEnabled`를 켜는 결정만
남습니다.

## 파일 이름

```
YYYY-MM-DD__<40자리 deploy SHA>.md
```

전체 SHA를 씁니다. 축약 SHA는 시간이 지나면 충돌할 수 있고, 무엇보다 어느
커밋인지 확인하려면 저장소를 뒤져야 합니다. 날짜가 앞에 오는 것은 목록이
시간순으로 정렬되게 하기 위해서입니다.

**merge SHA를 옮겨 적지 말고 실행 시점에 `GET /api/build-info`를 읽으십시오** —
그 endpoint는 로그인 없이 열립니다. staging은 develop에 무엇이 병합되든
재배포되므로, 병합 SHA와 서빙 SHA는 자주 다릅니다.

## 규칙

1. **기록은 덮어쓰지 않습니다.** 재검증은 새 파일입니다.
2. **비어 있던 항목을 나중에 통과로 채우지 않습니다.** 실행하지 않은 항목은
   `미기록`이며, 그것이 사실입니다.
3. **한 기록은 자기가 실행된 template revision을 적습니다.**
4. **동결된 기록은 digest로 보호합니다.** `frozen: true`인 기록은
   `npm run check:staging-verification-records`가 본문 digest를 대조합니다.
5. **실행·판정·서명은 사람이 합니다.** 통과·조건부·실패의 **판정**과 **서명**은
   사람만 씁니다. 그 둘은 에이전트가 비워 둡니다.

   **관측을 옮겨 적는 것은 에이전트가 합니다.** 실행자가 보고한 것 — 어떤 카드가
   어떤 순서로 보였고, 타이핑한 문장이 무엇이었고 클릭 후 무엇이 남았는지 — 을
   항목·관측 칸에 채워 초안을 만듭니다.

   경계는 **관측과 판정**입니다. "카드가 여섯 개 보였고 여섯 번째가 잠겨
   있었다"는 관측이고, "그러므로 이 회차는 통과다"는 판정입니다. **지어낸
   관측은 어느 쪽에서도 허용되지 않습니다.**

## 이 기능에만 있는 것 셋

**첫째, 유료 turn이 0회입니다.** 이 표면은 provider를 부르지 않고 크레딧을
예약하지 않습니다. 차단 항목 9개가 전부 무료이므로, 비용을 이유로 차단 구획을
미룰 근거가 없습니다.

**둘째, 정답지가 계산되어 있습니다.** 어느 카드가 보여야 하는지는 두 flag, 네
capability, 플랜, 화면 상한과 예약된 잠금 자리가 함께 정하므로 화면 앞에서
추론할 일이 아닙니다.

```
npm run report:starter-catalog-expectations -- --image=<on|off> --voice=<on|off> --brave=<on|off>
```

앱과 같은 순수 함수를 부릅니다. 이 표와 화면이 어긋나면 둘 중 하나가 결함이고,
그것이 이 검증이 찾는 것입니다.

**셋째, 차단 사유가 셋뿐이고 각각 한 줄로 적힙니다.** B(없는 기능을 약속한
카드를 보고 한 가입·결제는 회수되지 않음), C(전송되지 않은 초안에는 이력
테이블이 없음), A(B의 회수 경로). 나머지는 고쳐서 배포하면 끝나는 것이며
차단이 아닙니다.
