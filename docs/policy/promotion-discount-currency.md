## 1. 이 문서가 생긴 이유

AUD 시장에서 Pro 월간 A$20.00에 USD 고정액 코드 `PAYMENTTEST27`($14 off)을
적용하면 주문 요약이 `-$14`와 **A$1.33 due today**를 표시하고, "결제 계속하기"가
영어 오류로 거절했습니다. A$1.33은 환율이 아니라 비율입니다 — $15에서 $14를 뺀
비율 93.3%를 호주 가격 A$20.00에 곱한 값이고, **그런 AUD 할인은 DB에도 Stripe에도
없습니다.**

계약 불일치 자체는 수정됐습니다(#624). validation이 Checkout과 같은 통화 판정을
하고, 요약은 청구 가능한 것만 그립니다. 이 문서는 그 수정이 **드러낸** 질문에
답합니다: 고정액 할인을 여러 통화로 확장할 것인가.

## 2. 결정

**신규 프로모션은 정률 할인만 허용합니다.**

고정액 할인(`discountAmountCents`)의 다중 통화 지원은 도입하지 않습니다. 기존
USD 전용 코드는 만료까지 grandfathering하고, 컬럼은 삭제하지 않습니다.

## 3. 왜 정률인가

1. **시장별 요금이 환산값이 아닙니다.** 카탈로그는 시장마다 따로 정한 값입니다.

   | | USD | AUD | EUR | KRW | CNY |
   |---|---|---|---|---|---|
   | Pro 월간 | $15.00 | A$20.00 | €14.00 | ₩20,000 | ¥99.00 |

   $15에 어떤 환율을 곱해도 이 네 숫자가 나오지 않습니다. 가격이 결정이므로
   **할인액도 결정**이지 계산 결과가 아닙니다.

   이 표는 2026-08-16에 갱신됐습니다(§8). 그 전에는 AUD A$23.00, CNY ¥108.00으로
   적혀 있었고 **어느 쪽도 청구되던 값이 아니었습니다** — 코드 기본값은 낡았고
   production은 override를 쓰고 있었습니다. 논거는 그대로입니다. 오히려 시장가가
   환산값이 아니라는 사실은, 그 값들이 따로 갱신될 수 있다는 이번 사례로 더
   분명해집니다.

2. **정률은 가격이 바뀌거나 통화가 추가돼도 의미가 유지됩니다.** 50% 할인은
   새 시장이 생겨도 그대로 50% 할인입니다. 고정액은 캠페인마다 5개 통화 값을
   finance가 승인하고 계속 관리해야 합니다.

3. **비용이 provisioning 하나가 아닙니다.** Stripe coupon `currency_options`,
   Admin UI, reconciliation, webhook 금액 검증, 캠페인 수정·폐기 경로가 함께
   바뀝니다.

4. **USD에서만 동작하는 공개 코드는 지역에 따라 쓸 수 없어** 마케팅·지원 비용을
   만듭니다. 이번 사건이 그 형태였습니다.

5. **현재 확인된 고정액 요구는 실제 캠페인이 아니라 테스트 코드**
   (`PAYMENTTEST27`)입니다. §6에서 이 전제를 확인합니다.

### 3.1 정률이 대체하지 **못하는** 경우

정률로 충분한 것은 목적이 "몇 % 할인"일 때입니다. 목적이 **"첫 달을 각 시장의
특정 금액으로 판매"** 라면 정률은 대체재가 아닙니다.

`discountPercent`는 `Int`입니다(Prisma `Int @default(0)`, Admin schema
`z.number().int().min(0).max(100)`). 따라서 $15를 정확히 $1.00으로 만드는
93.333…%는 **표현할 수 없습니다.**

| | 결과 |
|---|---|
| $14 고정액 off $15 | **$1.00** |
| 93% | $1.05 |
| 94% | $0.90 |
| A$20의 93% | A$1.40 |
| €14의 93% | €0.98 |

이 경우에만 다중 통화 고정 프로모션을 도입할 사업적 이유가 생깁니다. §5가 그
조건입니다.

## 4. 기존 고정액 코드의 처리

컬럼과 기존 코드는 남기되, **범위를 넓히는 편집은 막고 좁히는 편집은 허용**합니다.
"편집 허용"으로 두면 신규 생성 차단이 우회됩니다.

| 동작 | 허용 |
|---|---|
| 신규 고정액 프로모션 생성 | **금지** |
| 비활성 고정액 코드 재활성화 | **금지** |
| 기존 고정액의 할인액 인상 | **금지** |
| 기존 고정액의 대상 플랜 추가 | **금지** |
| 기존 고정액의 기간 연장 (종료일 연기, 상환 상한 인상) | **금지** |
| 기존 코드 비활성화 | 허용 |
| 기존 코드 종료일 단축 | 허용 |
| 정률로 전환 | **기존 코드를 변형하지 말고 새 코드 생성** |

기존 활성 코드는 **USD-only로 명시**하고 만료까지 유지합니다. 마케팅·지원 문구에
그 제약이 드러나야 합니다.

"넓히는 편집"에는 행렬에 적힌 것 외에 두 가지가 더 포함됩니다. 둘 다 신규 생성
차단을 우회하는 경로이기 때문입니다.

- **코드 문자열 변경.** 만료된 고정액 코드의 이름을 새 캠페인 코드로 바꾸면 새
  배포 표면이 생깁니다. 그것이 이 정책이 막는 생성입니다.
- **시작일 앞당기기·삭제, 적용 개월 수 연장.** 종료일 연기와 같은 종류의
  기간 확대입니다.

정률 프로모션은 이 절의 대상이 아닙니다. 고정액을 갖지 않는 프로모션의 편집은
평소대로입니다.

마지막 항목이 중요합니다. 고정액 코드를 정률로 "바꾸면" 같은 코드 문자열이
시점에 따라 다른 할인을 뜻하게 되고, 이미 상환된 기록과 대조가 안 됩니다.
`pricingVersion`을 snapshot에 저장하고 가격 변경을 소급 적용하지 않는 기존 규율
(`docs/policy/credit-and-cost-limits.md`)과 같은 이유입니다.

## 5. `discountAmountCents` 컬럼

**당장 삭제하지 않습니다.** 과거 감사 데이터가 참조합니다 —
`BillingPromotionRedemption`은 상환 시점의 프로모션을 가리키고, 그때 어떤 할인이
적용됐는지는 재구성할 수 있어야 합니다.

삭제는 아래를 모두 확인한 뒤 **별도 migration**으로 합니다.

1. 활성 고정액 코드 0개
2. 예약(미시작) 고정액 코드 0개
3. 과거 데이터 의존성 없음 — 감사·정산·리포트 어느 경로도 이 컬럼을 읽지 않음

## 6. Rollout 조건 — production inventory

**아래를 확인하기 전에는 Admin 차단을 배포하지 않습니다.** 읽기 전용 조사입니다.

- 활성 고정액 코드의 수와 목록
- 각 코드의 캠페인 소유자, 노출 국가, 종료일
- 예약(startsAt 미래) 및 만료 고정액 코드

결과에 따라 갈립니다.

- **활성 0개**: 신규 생성과 재활성화를 즉시 차단하고 컬럼을 deprecated 처리할 수
  있습니다.
- **활성 있음**: 코드별로 소유자·노출 국가·종료일을 확인하고 전환 계획을 세운 뒤
  차단합니다. 차단이 진행 중인 캠페인의 운영을 막아서는 안 됩니다.

차단은 **Admin UI뿐 아니라 Admin API에서도** 적용합니다. UI만 막으면 API가 우회
경로가 됩니다.

### 6.1 확인 결과 (2026-08-16, `@mposition`)

- 활성 고정액 코드 **0개**
- `PAYMENTTEST27` 비활성 처리 완료
- 따라서 **"활성 0개" 분기**이며, 진행 중인 캠페인을 끊을 위험 없이 차단할 수
  있습니다.

이 결과는 조사 시점의 사실입니다. 이후에 고정액 코드가 다시 생기지 않는다는
보장은 조사가 아니라 **차단 자체**가 합니다.

### 6.2 강제 위치

- 판정: `lib/billingPromotionAdminPolicy.ts`의 `fixedAmountPromotionRefusal()`
  — 순수 함수 하나이며 Admin API와 Admin 패널이 같은 함수를 호출합니다.
  §4 행렬을 두 번 읽지 않습니다.
- API: `app/api/admin/billing/route.ts`의 PATCH가 **어떤 write보다 먼저** 검사해
  거절합니다. plan·price·promotion이 한 요청에 실려 오므로, 늦게 거절하면
  절반만 적용된 상태가 남습니다. 응답은 400 + `PROMOTION_FIXED_AMOUNT_BLOCKED`.
- UI: `components/admin/BillingAdminPanel.tsx`가 고정액 입력란을 저장된 행 기준
  으로 잠그고 사유를 그 자리에 적습니다. 저장 시점에만 막지 않습니다.
- 판정은 **저장된 행과 비교**합니다. 패널이 매 저장마다 프로모션 목록 전체를
  PATCH하므로, 요청 본문만 보고 고정액을 전부 거절하면 기존 코드가 하나라도
  있는 동안 billing 폼 전체가 잠깁니다.

## 7. 향후 도입 조건

다중 통화 고정액을 도입하려면 **모두** 충족해야 합니다.

1. 실제 캠페인 요청이 존재할 것 — "첫 달 A$1 / €1 / ₩1,000" 같은, 시장별 목표
   금액이 사업적으로 정해진 요청. 테스트 코드나 가정은 근거가 되지 않습니다.
2. **finance-ops가 각 통화의 값을 승인**할 것. 승인 주체는 finance-ops이며,
   승인 없이는 어떤 값도 저장하지 않습니다.
3. 캠페인 수정·폐기와 Stripe 쿠폰 버전 관리 절차가 함께 정해질 것.

### 7.1 표현 형태

도입한다면 `discountAmountByCurrency`보다 캠페인의 본뜻을 담는 형태를 검토합니다.

```
targetPriceByCurrency:
  USD: 100
  AUD: 100
  EUR: 100
  KRW: 1000
  CNY: 500
```

"얼마 할인"이 아니라 **"최종 얼마에 판매"** 하는 캠페인이라면 이 표현이 더
정확합니다. 요금제 가격이 바뀌면 할인액은 의미를 잃지만 목표가는 유효합니다.

절대 조건:

- **승인된 시장별 값만 사용합니다.** 환율로도, 가격 비율로도 값을 생성하지
  않습니다. 그 생성이 이 문서를 만든 사건입니다.
- 값이 없는 통화는 **적용 불가**입니다. 비워 두고 다른 통화에서 유도하지
  않습니다.
- plan · billing interval · **가격 버전(`pricingVersion`)별로 범위를
  제한**합니다. 목표가는 특정 가격표 위에서만 뜻이 있습니다.
- Stripe에는 해당 시점의 `amount_off`로 변환해 **별도 쿠폰 버전**을 생성합니다.
  Stripe는 `currency_options`로 통화별 할인액을 지원하지만 **자동 환산이
  아니며**, 쿠폰의 금액·통화 속성은 생성 후 변경에 제약이 있습니다. 값이 바뀌면
  새 쿠폰이고, 그 버전 관리는 운영 절차입니다.

## 8. 이 문서가 다루지 않는 것 — 가격 카탈로그 override

**해소됨(2026-08-16, #637).** 프로모션 정책과는 여전히 별개인 가격 거버넌스
문제이며, §2의 결정과 무관하게 진행됐습니다.

사고 화면의 Pro 월간 **A$20.00**은 `AppSetting`의 `billingPriceCatalog`
override였고, 코드 기본값은 A$23.00이었습니다. `npm run report:billing-price-catalog`
로 production을 읽은 결과:

- override는 정상 저장·유효 상태였고 **AUD만이 아니라 20건**을 덮고 있었습니다
  (AUD·CNY 플랜, 비 USD 크레딧팩 전부, Max 연간·KRW).
- 한 actor가 **한 번의 Admin API 요청**으로 저장했고, `AdminAuditLog` 항목이
  행의 `updatedAt`과 일치합니다.
- 코드 기본값은 그 20건에 대해 낡아 있었습니다.

기본값을 저장값에 맞췄습니다. **청구액은 바뀌지 않습니다** — override가 유효한
동안은 override가 이기고, 이 정렬은 override가 사라졌을 때의 값만 정합니다.

되돌리기 금지 지침은 이제 방향이 반대입니다. **기본값을 A$23으로 되돌리지
않습니다.** 그것은 승인된 적 없는 값이며, 되돌리면 override 유실 시 실제 가격
인상이 됩니다.

`AdminAuditLog`는 가격이 바뀌었다는 사실만 남기고 **이전·이후 값은 남기지
않습니다**(`localizedPricesUpdated` boolean). 가격 이력 재구성은 불가능하며,
이는 이 문서와 `AGENTS.md`가 함께 기록하는 별개 gap입니다 — #637이 닫힌 뒤에도
사라지지 않도록 여기 남깁니다.

### 8.1 Stripe 쪽 대조 (2026-08-25, #637 종결)

2026-08-16에 확인한 것은 **DB 절반**이었습니다 — 저장된 override와 그것을 쓴
actor. 남아 있던 것은 Stripe에 실제로 있는 값이었고, 이 저장소가 답할 수 없어
`blocked on production access`로 남아 있었습니다. livemode 읽기로 마저 확인했습니다.

**#637이 제기한 핵심 위험 — "가격 출처가 둘인데 대조하는 것이 없다" — 은 실재하지만
오늘 두 출처가 완전히 일치합니다.** Checkout은 카탈로그에서 `price_data`를 즉석
생성하고, plan change는 `BillingPlan.stripePriceId`가 가리키는 기존 Price 객체를
씁니다. 그 Price 객체 전수와 카탈로그를 대조한 결과:

| 플랜 | 통화 | 카탈로그 월/연 | Stripe Price 월/연 |
|---|---|---|---|
| Pro | AUD | 2,000 / 19,200 | 2,000 / 19,200 |
| Pro | CNY | 9,900 / 95,000 | 9,900 / 95,000 |
| Pro | EUR | 1,400 / 13,400 | 1,400 / 13,400 |
| Pro | KRW | 20,000 / 192,000 | 20,000 / 192,000 |
| Max | AUD | 3,900 / 37,400 | 3,900 / 37,400 |
| Max | CNY | 18,000 / 172,800 | 18,000 / 172,800 |
| Max | EUR | 2,300 / 22,000 | 2,300 / 22,000 |
| Max | KRW | 35,000 / 336,000 | 35,000 / 336,000 |

AUD 크레딧팩도 같습니다 — 700 · 1,400 · 2,800이 Starter · Project · Power Pack의
Price와 일치합니다. USD는 이 표 밖이며 `BillingPlan`에서 옵니다(Pro 1,500 / 14,400,
Max 2,500 / 24,000).

**실제 발행된 AUD Checkout Session도 같은 값입니다.** Pro 월간 두 건이
`amount_subtotal: 2000`, Max 월간 한 건이 `3900`, project_1500 크레딧팩 한 건이
`1400`이고 그 건의 `billingExpectedAmountMinor` 메타데이터도 `1400`입니다. KRW Max
월간 한 건은 `35000`입니다.

**되돌리기의 영향 범위는 비어 있습니다.** livemode 구독은 3건뿐이고 전부 USD ·
Pro 월간 · $15.00 · 취소됨이며 `PAYMENTTEST` 프로모션이 붙은 시험 거래입니다.
**AUD 구독은 0건**이므로, #637 초안이 걱정한 "기존 호주 구독자 재청구"는 대상이
없습니다. 그렇다고 기본값을 A$23으로 되돌려도 되는 것은 아닙니다 — 위 규칙 그대로,
그 값은 승인된 적이 없습니다.

**A$20.00은 승인된 가격입니다.** 사고로 보고된 화면이 옳았고, 낡아 있던 것은 코드
기본값이었습니다. localized Price 객체 16개는 2026-07-15 11:31–11:41 UTC의 10분
창에 만들어졌습니다 — 한 번의 의도된 작업이며, 한 달 뒤 기본값이 그쪽에 맞춰졌습니다.

관측 하나를 함께 남깁니다. 모든 Session이 `adaptive_pricing.enabled: true`입니다.
오늘은 통화와 금액을 앱이 정하고 Stripe가 그것을 덮지 않는 것이 위 실측으로
확인되지만, 이 설정이 켜져 있다는 사실 자체는 기록해 둘 값어치가 있습니다.

## 9. 이미 반영된 것

이 문서의 결정과 별개로, 계약 불일치는 수정돼 배포 경로에 올라 있습니다.

- 통화 판정이 `promotionCurrencyFailure()` 한 곳에 있고,
  `validatePromotionForCheckout()`이 `currency`를 필수 인자로 받습니다.
- validation이 Checkout과 같은 `validateBillingMarketRequest()` 계약을 씁니다.
- Checkout이 같은 검사를 Stripe·lease·redemption **이전에** 재실행합니다.
- 거절은 `PROMOTION_CURRENCY_NOT_SUPPORTED`이고 7개 언어로 현지화됩니다.
- 주문 요약은 청구 가능한 프로모션만 그립니다.

즉 **오늘도 비 USD 고정액 코드는 사용할 수 없습니다.** 이 문서는 그 상태를 정책
으로 확정하고 확장하지 않기로 하는 것이지, 되던 것을 막는 것이 아닙니다.
