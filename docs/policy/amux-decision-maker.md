# AMUX Decision Maker

상태: **초안 — 승인 대기. 구현 없음.** 최초 작성 2026-10-07.

| 버전 | 승인 | 변경 |
|---|---|---|
| 1 | **승인 대기** | 최초 초안. 2026-10-07 운영자가 대화에서 정한 결정(§0)을 담는다. 독립 검토 두 회차의 지적을 반영한 세 번째 초안이다. |

이 문서는 운영자가 `approvedBy`·`approvedAt`을 기록하기 전까지 구현 근거가 아니다(공통 기반
원칙 1). 이 정책은 두 개정을 전제로 하며, 각각 운영자가 따로 승인한다.

- **공통 기반 r16:** 원칙 3(선택지 고르기 자율 답변), 원칙 11(DM 세션의 실행 위치), §3(저장소
  스냅샷 전송), §4(질문·답 본문의 앱 DB 저장)의 좁은 예외.
- **오케스트레이션 정책의 새 버전**(다음 빈 번호): 전용 Ubuntu runner의 worker 목록에 DM 세션 둘을
  §6의 격리 조건으로 더한다. 이 정책은 그 목록을 스스로 넓히지 않는다.

두 개정이 승인되기 전에는 §12의 해당 단계를 시작하지 않는다. 승인돼도 각 단계의 독립 검토는 그대로다.

## 0. 운영자 결정 (2026-10-07)

1. DM이 답할 수 있는 질문 유형은 `decision`, `judgment`, `budget`, `credential`, `access`,
   `external`이다. `customer_outbound`는 항상 운영자. 되돌릴 수 없는 행위는 유형과 무관하게 운영자.
2. 시작은 제안 모드. 자율 졸업은 운영자가 결정한 제안 **50건**, 첫 제안 뒤 **30일**, 수정 없이
   확정한 비율 **95%** 이상.
3. DM은 공급사를 교차한 두 개(GPT-6 Astra, Claude Fable 5.1).
4. 자율 답변을 위해 공통 기반 원칙 3을 개정한다.
5. DM은 질문 카드와 묻는 worker의 저장소를 읽는다.
6. 기록은 Tomverse 앱 DB와 해시 체인 감사에 둔다.
7. DM은 Tomverse AMUX의 추가 worker로 둔다.
8. 코드·문서·테스트 변경 선택지도 경로 검사를 통과하면 자율 대상이다.
9. 운영자는 제안을 Tomverse Admin에서 확정한다.

## 1. 목적과 경계

AMUX worker가 운영자의 답을 요구하는 질문(로컬 AMUX board의 typed ask)을 운영자에게 보내기 전에
DM이 먼저 받는다. DM이 답하면 worker는 그 답으로 이어서 일한다. DM이 답할 수 없거나 아래 조건을
넘으면 질문은 운영자에게 간다.

DM은 **질문에 답하는 worker이지 승인자가 아니다.**

- `docs/policy/amux-agent-approval-contract.md`(이하 승인 계약)의 작업 검토·외부 행위 승인,
  `docs/policy/development-agent-orchestration.md`(이하 오케스트레이션 정책)의 승격·자동 승격·완료
  확정, PR 병합, 배포, 그 밖에 사람 actor를 요구하는 모든 게이트에서 DM은 사람으로 인정되지 않는다.
  DM의 시스템 actor는 닫힌 목록 항목이고 `auditRowActorKind()`가 사람으로 판정하지 않는다.
- DM의 답은 묻는 worker가 **이미 할 수 있는 일**만 허락한다. worker 계정에는 제품 DB·배포·main
  병합·외부 발송 권한이 없다(오케스트레이션 정책 v23). DM의 답이 그 권한을 만들지 않는다.
- DM은 자기 라우팅 규칙, 효과 등급, 경로 분류, 스위치, 졸업 기록, 이 정책, 정책 테스트를 고칠 수
  없다(원칙 6). 경로 분류의 원천인 `lib/agentAuthorityFiles.ts`는 사람이 소유한다.

## 2. 흐름

1. worker가 typed ask를 올리면 로컬 AMUX가 bridge(오케스트레이션 정책 v23의 outbound 경로)로 앱
   내부 route에 요청을 보낸다. **카드는 route가 DM 배정을 돌려줄 때까지 운영자 대기열에 그대로 있다.**
   route 실패·bridge 실패·2분 안 무응답이면 카드는 운영자 대기열에 남는다(fail-closed).
2. **앱 내부 route(결정적 판정, LLM 없음)** 가 §3으로 정하고, 요청 행과 시스템 감사를 같은 트랜잭션에
   쓴다. 결과는 `operator`, `dm_proposal`, `dm_autonomous` 중 하나다.
3. DM 배정이 오면 로컬 AMUX가 카드를 DM 대기 표시로 옮기고, §5의 입력을 만들어 배정된 DM 세션에 준다.
   이 시점부터 시간 초과·실패·이관은 카드를 운영자 대기열로 되돌린다.
4. DM의 구조화된 출력을 bridge가 route로 보낸다. route가 §6으로 검증하고 최종 결과를 정한다.
5. 제안은 Tomverse Admin에서 운영자가 확정·수정 후 확정·거절한다. 권한은 `ops:write`와 최근
   step-up이고 판정은 사람 감사로 남는다(승인 계약 §2와 같은 조건).
6. 전달할 답이 정해지면 bridge가 가져가고, 로컬 AMUX가 기존 운영자 답변 경로(worker 세션 메시지 +
   카드 기록)로 전달하며 전달 영수증을 보고한다. 메시지는 §7의 표시로 시작한다.

## 3. 라우팅 — 앱 route의 결정적 판정

두 단계로 판정한다. **A의 검사는 모두 실행**하고 하나라도 걸리면 운영자다. A를 통과한 질문만 B로
제안·자율을 정한다.

**A. 운영자로 보내는 검사**

1. 전체 kill switch가 켜짐, 배정될 인스턴스 스위치가 `off`, 설정을 읽지 못함.
2. `ask_type`이 허용된 여섯(§0-1) 밖. `customer_outbound`도 여기다.
3. 되돌릴 수 없는 행위 용어 목록에 걸림. 판정 입력은 카드의 type·tag·제목·질문·선택지·해제 조건.
   목록은 정책 버전에 묶인 추가 거절 필터이며 효과 등급(B)을 대신하지 않는다. 초안 범주: main 병합,
   ship·release·배포·production, 삭제·delete·drop·truncate·덮어쓰기, migration, 결제·환불·청구, 외부
   게시·발송·연락, secret·token·password·API key의 제공, 권한·접근 설정 변경, 정책·workflow·branch
   protection 변경.
4. 유형별 조건:
   - `budget`: 구조화된 금액(USD)이 없음, 한도를 올리는 질문, 또는 앱 DB의 30일 DM 지출 원장에서
     **같은 트랜잭션의 잠금 아래** 잔액을 예약하지 못함. 한도 기본값은 0이고 운영자만 정한다. 예약은
     (카드 id, 질문 revision)당 하나이며 운영자 거절·이관·시간 초과·늦은 결과 거절에서 해제되고, 자율
     전달이나 운영자 확정에서 확정된다.
   - `credential`: 비밀값을 제공해야 끝나는 질문. DM은 비밀값을 받지도 주지도 않는다.
   - `access`: 권한·접근 설정을 바꿔야 끝나는 질문.
   - `external`: 제3자에게 연락해야 끝나는 질문.
   위 세 유형은 worker가 `resolution`(`needs_secret`·`needs_permission_change`·`needs_contact` 또는
   `decision_only`) 필드로 밝히며, `decision_only`가 아니면 운영자다.
5. 묻는 worker의 모델 공급사가 확인되지 않음(§7).
6. 처리량 초과: 인스턴스마다 시간당 20건, 하루 100건.
7. 입력 한도 초과(§5).

**B. 제안과 자율**

- 질문의 모든 선택지가 §4의 자율 조건을 통과하고, 그 인스턴스가 `autonomous`이면 `dm_autonomous`.
- 그 밖에는 `dm_proposal`. 선택지가 없는 질문도 제안으로 DM에게 간다.

DM의 출력은 질문을 **운영자 쪽으로만** 옮길 수 있다. 제안 대상이 DM 출력으로 자율 대상이 되지 않는다.

## 4. 자율 답변의 범위 — 공통 기반 r16 원칙 3 예외

자율 모드에서 DM이 하는 일은 **worker가 낸 선택지 중 하나를 고르는 것**뿐이다. 선택지 집합, 효과 등급,
경로, 예산 잔액, 모드는 앱 route의 결정적 코드가 검증하고, LLM은 그 안에서 하나를 고른다. 자유 서술 답은
자율로 전달하지 않는다.

| 효과 등급 | 뜻 | 자율 조건 |
|---|---|---|
| `choice_only` | 정보·방향 선택. 그 자체로 파일이 바뀌지 않는다. | 없음 |
| `wait_or_defer` | 기다리거나 다른 작업을 먼저 한다. | 없음 |
| `branch_code_change` | 그 worker의 작업 브랜치에서 코드 변경 | 경로 검사 |
| `docs_change` | 작업 브랜치의 문서 변경 | 경로 검사 |
| `test_change` | 작업 브랜치의 테스트 변경 | 경로 검사 |
| 그 밖의 모든 것 | 목록에 없는 효과 | 제안만 |

**경로 검사:** 변경 등급 선택지는 바꿀 저장소 경로 목록(1~50개)을 갖는다. 모든 경로가
`lib/agentAuthorityFiles.ts`의 분류에서 `product`일 때만 자율이다. `control-plane`·`unclassified`, 알
수 없는 최상위 디렉터리, 경로 목록 누락은 제안이다. 이 분류는 엔지니어링 Agent의 게시 등급이 쓰는
것과 같고, 정책 문서·정책 테스트·workflow·`AGENTS.md` 같은 게이트 파일은 `product`가 아니다.

**사후 대조:** 자율 답 뒤 그 worker의 작업 브랜치에서 생긴 commit의 변경 경로를 bridge가 관측해 선언한
경로와 같은 분류로 대조한다. 선언 밖의 경로나 `product`가 아닌 경로가 나오면 운영자 알림을 열고 운영자
정정 1건으로 센다(§8 강등). 등급·경로 목록이나 분류 기준의 변경은 정책 버전 변경이다.

## 5. DM의 입력과 격리 — 공통 기반 r16 §3 예외

- **카드:** 질문 카드의 구조화된 필드(유형·질문·선택지·효과 등급·경로·해제 조건·worker가 적은 맥락)만.
  상위·의존 카드는 넣지 않는다. 카드 텍스트는 합계 16 KiB 이하. 카드의 URL을 가져오지 않는다.
- **저장소 스냅샷:** 묻는 worker의 Git worktree를 그 worker의 현재 HEAD에서 뜬 Git 추적 파일만.
  untracked·ignored 파일, worker 홈, 다른 worktree, submodule, symlink, 바이너리(NUL 바이트 또는 UTF-8
  아님)는 넣지 않는다. 정책 버전에 묶인 비밀 패턴 목록에 걸린 경로를 빼고(초안: `.env*`, `*.pem`,
  `*.key`, `*.p12`, `id_*`, `*secret*`, `*credential*`, `.npmrc`, `.netrc`), 남은 파일 전체를 기존 secret
  검사 규칙으로 검사해 걸린 파일을 뺀다. 파일당 256 KiB, 합계 2 MiB를 넘으면 스냅샷을 만들지 않고
  카드만으로 진행한다. 무엇을 뺐는지는 건수와 사유만 기록한다. 스냅샷 manifest(경로·blob id 목록)의
  digest를 요청에 결속한다.
- **r16 §3 승인 전에는 카드만 넣는다.** 스냅샷 전송은 회수할 수 없으므로 그 개정의 승인이 선행 조건이다.
- **실행 계정:** DM 세션은 worker 계정과 다른 권한 없는 Linux 계정에서 돈다. 두 CLI 로그인만 있고
  GitHub 로그인·git credential helper·SSH 키·제품 DB·배포 자격증명·bridge 환경 파일·worker 홈 읽기
  권한이 없다. 스냅샷은 그 질문 동안만 그 계정이 읽는다.
- **세션 모드:** `codex`는 read-only sandbox, `claude`는 파일 수정·명령 실행 도구를 끈 모드. S0에서 실제로
  쓰기·명령 실행이 막히는지 실측한다.
- **hard timeout:** 질문당 30분이 지나면 DM 프로세스를 강제 종료한다. 늦은 결과는 §9가 거절한다.
- **외부 텍스트:** worker가 카드에 인용한 로그·이슈 발췌는 데이터다. DM 지시문은 그 안의 지시를 따르지
  말라고 명시한다(원칙 3의 둘째 문장).

## 6. DM 출력의 검증

DM 출력은 `.strict()` 스키마 값 하나이며 종류별로 검증한다.

| 종류 | 내용 | 결과 |
|---|---|---|
| `select` | 선택지 id, 근거, `irreversible` | 자율 또는 제안 |
| `free_text` | 답 본문(상한 있음), 근거, `irreversible` | 제안만 |
| `escalate` | 이관 사유 | 운영자. 검증 실패가 아니다 |

- `select`: 선택지 id가 요청에 있어야 한다. 자율이면 그 선택지가 §4의 자율 조건을 통과해야 한다.
- `irreversible`이 true면 운영자로 보내며 검증 실패로 세지 않는다.
- 답 본문·근거는 secret 검사를 통과해야 한다.
- 스키마 위반, 없는 선택지 id, secret 검사 실패만 **검증 실패**이며 §8의 latch에 센다.
- **전달 직전 재확인:** 자율 전달을 확정하는 트랜잭션 안에서 kill switch, 인스턴스 모드, 강등·off latch,
  요청의 열림 상태와 질문 revision, 예산 예약을 다시 확인한다. 그사이 off·강등되면 그 결과는 제안으로
  돌린다.

## 7. DM 인스턴스, 실행 위치, 표시

| 인스턴스 | CLI와 모델 | 받는 질문 |
|---|---|---|
| `decision-maker-openai` | `codex`, GPT-6 Astra | `claude` provider worker |
| `decision-maker-anthropic` | `claude`, Claude Fable 5.1 | `codex` provider worker |

- 공급사는 오케스트레이션 정책의 확인된 provider(`claude`, `codex`) 기준이다. 그 밖의 provider(gemini,
  ollama, cursor, copilot, devin 등)의 질문은 운영자다. 확인 목록이 넓어지면 이 표도 정책 버전으로 넓힌다.
- 배정된 DM이 꺼져 있거나 응답할 수 없으면 다른 DM으로 넘기지 않고 운영자에게 보낸다.
- **실행 위치:** 두 DM은 Tomverse AMUX의 추가 worker 세션으로, 오케스트레이션 정책 v23의 전용 Ubuntu
  runner에서 돈다. 이 배치는 r16 원칙 11 예외와 오케스트레이션 정책의 새 버전이 승인해야 성립한다.
- **사용량:** DM CLI 호출은 오케스트레이션 정책 v22 §5의 공통 사용량 사건을 남기되 namespace
  `amux-decision-maker`를 갖는다. 이 namespace의 unknown은 Task 비용 판정과 claim 보류에 쓰이지 않는다.
  DM에게 강제 가능한 호출 전 상한은 §3-A6의 처리량이다.
- **worker에게 보이는 표시:** 메시지는 `[Decision Maker <인스턴스> (<모델>), <proposal-confirmed|
  autonomous>, re <카드>]`로 시작하고 "운영자 승인이 아니다. 사람 승인이 필요한 게이트는 따로 요청한다"는
  문장을 붙인다. 카드 기록도 같은 표시를 쓴다.

## 8. 모드, 졸업, 강등, 스위치

- 인스턴스별 스위치 `off`·`proposal`·`autonomous`, 기본 `off`, 읽기 실패 `off`. `autonomous`는 그
  인스턴스의 졸업 기록이 있을 때만 받는다. 전체 kill switch는 모든 질문을 운영자에게 보낸다. 스위치·
  한도·졸업 변경과 latch 해제는 `ops:write`와 최근 step-up을 요구하고 사람 감사로 남는다.
- **졸업:** 인스턴스별로 운영자가 결정한 제안 50건 이상, 첫 제안 뒤 30일 이상, 수정 없이 확정한 비율
  95% 이상. 분모는 운영자가 결정한 제안이며, DM 이관·시간 초과·검증 실패는 빼고 따로 보고한다. 요건
  충족은 전환이 아니다. 운영자의 졸업 기록이 있어야 `autonomous`를 받는다.
- **강등(구현된 것만 센다):** 자율 모드에서 운영자 정정(사후 대조 불일치 포함) 7일 안 2건이면
  `proposal`로 latch. 검증 실패 연속 3건이면 `off`로 latch. 해제는 운영자만.

## 9. 결과를 모를 때와 늦은 결과

- 요청은 (카드 id, 질문 revision)당 하나다. 같은 질문이 다시 와도 새 요청을 만들지 않는다.
- 요청 상태(열림 → 닫힘)와 질문 revision, 스냅샷 manifest digest, 정책 버전, 효과 등급·경로 분류·
  scanner 버전이 결정에 결속된다. 닫힌 요청이나 결속 값이 바뀐 요청에 도착한 결과는 거절을 기록한다.
- worker에게 답을 전달한 결과가 불명확하면 다시 보내지 않는다. 그 요청을 `delivery_unknown`으로 두고,
  **그 worker 세션을 일시 정지**(AMUX pause)한 뒤 로컬 메시지 멱등 키로 전달 영수증을 조회한다. 확정되지
  않으면 운영자에게 넘기고 DM의 답과 "전달 여부 미확인"을 함께 보인다. 운영자가 확인하고 재개하기 전에는
  다른 답을 보내지 않는다(원칙 7).

## 10. 기록, 본문, 보존 — 공통 기반 r16 §4 예외

- **결정 원장(변경 불가):** 요청, DM 결과, 운영자 판정, 전달 영수증, 예산 원장 항목, 모드 기록을
  append-only 행으로 둔다. 상태는 새 행으로 남기며(요청 열림·닫힘, 예약 생성·확정·해제), UPDATE·DELETE는
  DB trigger가 막는다. 본문은 원장에 넣지 않는다. 본문 식별은 서버 키의 keyed digest로 하며 평문 hash를
  두지 않는다.
- **본문 저장소(분리):** 운영자가 Admin에서 판단하려면 질문과 DM 답의 본문이 필요하다. 이 둘만 별도 표에
  상한 있는 텍스트로 둔다. 업로드 전에 secret 검사를 통과해야 하고, 요청이 닫힌 뒤 90일에 본문 행을
  지운다. 그 표의 DELETE는 보존 기한이 지난 행에 대해서만 trigger가 허락한다. 본문은 감사 metadata·로그·
  알림에 넣지 않는다. 저장소 스냅샷은 앱으로 보내지 않는다.
- **actor:** `amux-decision-router`, `amux-decision-maker-openai`, `amux-decision-maker-anthropic`을 닫힌
  시스템 actor 목록에 리뷰로 추가한다. 모든 쓰기는 `writeSystemAuditLog()` 또는 사람 감사와 같은 트랜잭션이다.
- 단일 writer 모듈이 위 표들에 쓴다.

## 11. 비용, 데이터, 법규

- DM은 구독형 CLI 계정을 쓴다. 공급사 청구액을 측정한다고 주장하지 않는다. 사용자 크레딧·플랜·Chat
  provider 예산과 닿지 않는다(원칙 5). `budget` 원장은 DM이 허락할 수 있는 **worker의 지출** 상한이다.
- 질문 카드와 스냅샷은 묻는 worker의 공급사와 **다른** 공급사로 추가 전송된다. 두 공급사 모두 이미 worker
  세션이 같은 저장소를 보내는 곳이다. 저장소·카드에 개인정보가 섞일 수 있으므로 S0에서 두 공급사의
  처리위탁·국외 이전 조건을 확인한다. 이 정책은 처리 region을 보장한다고 쓰지 않는다. 중국 본토 접속·처리
  region·그 지역 공급자는 쓰지 않는다.
- DM은 고객 대면 문구를 만들지 않는다.

## 12. 단계

1. **S0(유료 turn 포함, 운영자 승인 필요):** 두 CLI의 두 모델 가용성, DM 계정의 읽기 전용 모드가 쓰기·
   명령 실행을 막는지, 구조화 출력, 강제 종료, 재시도·중복 응답 형태, 두 공급사의 처리위탁 조건 → CLI별
   복구 계약 표.
2. **S1:** 앱 DB(원장·본문 표·trigger·단일 writer), 라우팅 route와 예산 원장, 시스템 actor, 스위치(기본
   `off`), 용어 목록·효과 등급·경로 검사의 테스트. DM 호출 없음.
3. **S2:** 로컬 AMUX(typed ask의 선택지·효과 등급·경로·금액·`resolution` 필드, DM 대기 표시, fail-closed
   복귀), bridge 경로, DM 계정과 세션, Admin 제안 화면. 제안 모드만, 카드 입력만. 오케스트레이션 정책의
   새 버전과 r16 원칙 11·§4 승인이 선행 조건이다. 서버 반영은 운영자 승인.
4. **S2b:** 저장소 스냅샷. r16 §3 승인이 선행 조건이다.
5. **S3:** 졸업 기록, 자율 모드, 전달 직전 재확인, 사후 대조, 강등 latch. r16 원칙 3 승인이 선행 조건이다.

차단 기준(되돌릴 수 없는 것): DM이 승인 게이트에서 사람으로 인정되지 않는다는 테스트, 용어 목록·효과 등급·
경로 분류의 거절 테스트, 예산 원장의 동시 예약 테스트, 읽기 전용 모드·DM 계정 격리의 S0 증거, 스냅샷의
비밀 제외 테스트.

## 13. 이 정책이 하지 않는 것

- 승인 계약, 오케스트레이션 정책의 게이트·승격·자동 승격·확인된 provider 목록을 바꾸지 않는다.
- 터미널의 대화형 질문(`AskUserQuestion` 등)에 키를 눌러 답하지 않는다(AMUX의 기존 규칙 유지). 도구
  실행 승인 화면에도 답하지 않는다.
- worker의 권한을 넓히지 않는다.
