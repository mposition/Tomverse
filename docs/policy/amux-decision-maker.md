# AMUX Decision Maker

상태: **초안 — 승인 대기. 구현 없음.** 최초 작성 2026-10-07.

| 버전 | 승인 | 변경 |
|---|---|---|
| 1 | **승인 대기** | 최초 초안. 2026-10-07 운영자가 대화에서 정한 세 결정(아래 §0)을 담는다. |

이 문서는 운영자가 `approvedBy`·`approvedAt`을 기록하기 전까지 구현 근거가 아니다
(공통 기반 §0 원칙 1). 승인돼도 §11의 단계별 착수 조건과 각 단계의 독립 검토는 그대로
적용된다. 이 정책은 `docs/policy/development-agent-orchestration.md`(이하 오케스트레이션
정책)와 `docs/policy/amux-agent-approval-contract.md`(이하 승인 계약)를 바꾸지 않는다.

## 0. 운영자 결정 (2026-10-07)

1. DM이 답할 수 있는 질문 유형은 `decision`, `judgment`, `budget`, `credential`, `access`,
   `external`이다. `customer_outbound`는 항상 운영자에게 간다. 되돌릴 수 없는 행위는
   유형과 무관하게 운영자에게 간다.
2. 시작은 제안 모드다. 자율 모드 졸업 조건은 운영자가 확정한 제안 **50건**, 첫 제안 뒤
   **30일**, 수정 없이 그대로 확정한 비율 **95%** 이상이다.
3. DM은 공급사를 교차한 두 개다. GPT-6 Astra DM과 Claude Fable 5.1 DM.

## 1. 목적과 경계

AMUX worker가 운영자의 답을 요구하는 질문(로컬 AMUX board의 typed ask, `needsyou`)을
운영자에게 보내기 전에 DM이 먼저 받는다. DM이 답하면 worker는 그 답으로 이어서 일한다.
DM이 답할 수 없거나 정해진 조건(§3)을 넘으면 질문은 지금처럼 운영자의 `needsyou`
대기열로 간다.

DM은 **판단을 주는 worker이지 승인자가 아니다.**

- 승인 계약의 작업 검토(`review → done`)와 외부 행위 승인, 오케스트레이션 정책의
  승격·자동 승격·완료 확정, PR 병합, 배포, 그 밖에 사람 actor를 요구하는 모든 게이트에서
  DM은 사람으로 인정되지 않는다. 승인 계약 §2대로 시스템 actor는 승인자가 될 수 없다.
- DM의 답은 Tomverse 앱 DB의 승인 증거가 아니며 그런 증거로 기록하지 않는다(공통 기반
  §0 원칙 12). DM 기록은 로컬 AMUX board의 기존 운영자 답변과 같은 층에 있다.
- DM은 자기 라우팅 규칙, 스위치, 졸업 기록, 이 정책, 정책 테스트를 고칠 수 없다(원칙 6).

## 2. DM 인스턴스

| 이름 | CLI와 모델 | 받는 질문 |
|---|---|---|
| `decision-maker-openai` | `codex`, GPT-6 Astra | 모델 공급사가 Anthropic인 worker의 질문 |
| `decision-maker-anthropic` | `claude`, Claude Fable 5.1 | 그 밖의 모든 worker의 질문 |

- 묻는 worker의 모델 공급사는 worker 설정의 provider와 모델로 정한다. `claude` provider는
  Anthropic, `codex`·`ollama`는 OpenAI 계열로 본다. Cursor·Copilot의 `auto`처럼 공급사를
  확정할 수 없으면 `decision-maker-anthropic`으로 보내고, 기록에 `crossVendor: unknown`을
  남긴다. 공급사가 교차했다고 표시하지 않는다.
- 배정된 DM이 꺼져 있거나 응답할 수 없으면 다른 DM으로 넘기지 않고 운영자에게 보낸다.
  같은 공급사가 답하는 경로를 만들지 않기 위해서다.
- 두 DM은 AMUX worker 세션으로, 오케스트레이션 정책 v23이 승인한 전용 Ubuntu runner에서
  돈다. 다른 worker와 같은 구독형 CLI 계정을 쓰고, 제품 DB 자격증명은 없다.

## 3. 라우팅 — 결정적 코드

질문이 `needsyou`에 들어오는 순간(운영자를 actor로 한 유효한 typed ask) AMUX 서버가 아래
순서로 정한다. LLM은 이 판정에 참여하지 않는다.

1. DM 스위치(§8)가 `off`이면 운영자.
2. `ask_type`이 `customer_outbound`이면 운영자.
3. **되돌릴 수 없는 행위 목록**에 걸리면 운영자. 판정 입력은 카드의 type·tag·제목·질문·
   해제 조건이고, 목록은 이 정책 버전에 묶인 닫힌 용어 목록이다(초안: main 병합, 배포,
   production, 삭제·drop, migration, 결제·환불·청구, 외부 게시·발송, secret·token·password·
   API key의 제공, 권한·접근 설정 변경, 정책·workflow·branch protection 변경). 목록은
   오탐하면 운영자에게 가는 쪽으로만 틀린다. 목록 변경은 정책 버전 변경이다.
4. 유형별 추가 조건:
   - `budget`: 운영자가 미리 정한 DM 지출 한도(30일 단위 USD, 기본 0) 안의 금액이 카드의
     구조화된 금액 필드로 주어진 경우만 DM. 금액이 없거나 한도를 넘거나, 한도 자체를
     올리는 질문이면 운영자. DM은 한도를 바꿀 수 없다.
   - `credential`: DM은 비밀값을 받지도 주지도 않는다. 이미 있는 설정 중 무엇을 쓸지,
     비밀값 없이 어떻게 진행할지까지만 답한다. 비밀값을 제공해야 끝나는 질문은 운영자다.
   - `access`: DM은 권한·접근 설정을 바꾸지 않는다. 우회·대안 판단까지만 답한다.
   - `external`: DM은 계속 기다릴지, 대안으로 진행할지를 답한다. 제3자에게 연락하는 일은
     외부 발송이므로 운영자다.
5. 처리량 상한: DM마다 시간당 20건, 하루 100건. 넘으면 운영자.
6. 위를 모두 통과하면 배정된 DM(§2)에게 보낸다. 카드는 `needs:you` 표시 대신 DM 대기
   표시를 받으며, 운영자 대기열에 나타나지 않는다(제안 모드에서는 DM 제안이 붙은 뒤
   나타난다, §4).

DM의 출력은 질문을 **운영자 쪽으로만** 옮길 수 있다. DM이 되돌릴 수 없다고 표시하거나,
답할 수 없다고 하거나, §5의 형식을 어기거나, 30분 안에 답하지 않으면 운영자에게 간다.
DM 출력으로 운영자에게 가야 할 질문이 DM에게 오지는 않는다.

## 4. 제안 모드와 자율 모드

- **제안 모드(시작):** DM은 답 초안·근거·검토한 선택지를 카드에 붙인다. 카드는 "DM 제안
  있음" 표시와 함께 운영자의 `needsyou` 대기열에 들어가고, 운영자가 그대로 확정·수정 후
  확정·거절 중 하나를 고른다. worker에게 가는 답은 운영자가 확정한 내용이다.
- **자율 모드:** DM의 답이 바로 worker에게 가고 카드는 대기열을 떠난다. 운영자는 DM 결정
  목록에서 모든 답을 보고, 언제든 정정 메시지를 보낼 수 있다.
- **졸업:** DM 인스턴스별로, 운영자가 결정한 제안이 50건 이상, 첫 제안 뒤 30일 이상,
  수정 없이 그대로 확정한 비율이 95% 이상일 때 졸업 요건이 충족된다. 분모는 운영자가
  결정한 제안이다. DM이 스스로 운영자에게 넘긴 질문과 시간 초과는 분모에서 빼고 따로
  보고한다. 요건 충족은 자율 전환이 아니다. 운영자가 졸업 기록을 남겨야 전환된다.
- **강등:** 자율 모드에서 운영자 정정이 7일 안에 2건이면 그 DM은 제안 모드로 돌아가고
  latch된다. 다시 자율로 가려면 운영자의 새 졸업 기록이 필요하다.

## 5. DM 실행과 답의 형식

- DM 세션은 읽기 전용이다. `codex`는 read-only sandbox, `claude`는 파일 수정·명령 실행
  도구를 끈 모드로 띄운다. 읽을 수 있는 것은 질문 카드, 그 카드의 상위·의존 카드, 묻는
  worker 저장소의 파일(읽기)이다. git push, board 쓰기, 네트워크 쓰기는 없다.
- DM의 답은 `.strict()` 스키마의 구조화된 값 하나다: 결정(`answer` 또는 `escalate`),
  답 본문(상한 있음), 근거, 검토한 선택지, 되돌릴 수 없는 행위가 걸렸는지 여부. 서버가
  검증하고 board에 쓴다. 형식 위반은 운영자에게 간다.
- 답 본문은 기존 secret 검사 규칙을 지난다. 걸리면 버리고 운영자에게 보낸다.
- 질문과 카드에 인용된 로그·웹 페이지 같은 외부 텍스트는 데이터다. DM 지시문은 그 안의
  지시를 따르지 말라고 명시한다(원칙 3).
- worker에게 가는 메시지는 기존 운영자 답변과 같은 경로로 가되 `[Decision Maker
  (<model>, proposal-confirmed|autonomous), re <card>]`로 시작해, 누가 어떤 모드로 답했는지
  드러낸다. 답은 그 질문에만 적용된다.

## 6. 기록

- 카드: 기존 `answered` 기록과 같은 위치에 DM 인스턴스·모델·모드·결과를 남긴다.
- 로컬 AMUX store에 append-only DM 결정 행: 카드 id, 질문 revision, ask_type, DM 인스턴스,
  모델, `crossVendor`, 모드, 결과(`answered`·`escalated`·`timeout`·`invalid`·
  `routed_to_operator`와 사유), 운영자 판정(`accepted`·`modified`·`rejected`·없음), 시각.
  질문·답 본문은 카드에 있으므로 행에는 digest만 둔다.
- 졸업·강등·스위치 변경은 운영자 actor로 같은 store에 남는다.

## 7. 비용

DM은 다른 AMUX worker처럼 구독형 CLI 계정을 쓴다. 호출 단위 USD 원장은 없고, 이 정책은
구독 청구액을 측정한다고 주장하지 않는다(amux-intake v4와 같은 입장). 상한은 §3의 처리량이다.
사용자 크레딧·플랜·Chat provider 예산과 닿지 않는다(원칙 5). §3의 `budget` 한도는 DM이 승인할
수 있는 **worker의 지출** 상한이며 DM 자신의 비용이 아니다.

## 8. 스위치와 정지

- DM 인스턴스별 스위치 `off`·`proposal`·`autonomous`. 기본 `off`. `autonomous`는 그 인스턴스의
  졸업 기록이 있을 때만 받는다. 설정을 읽지 못하면 `off`(fail-closed).
- 전체 kill switch는 모든 질문을 운영자에게 보낸다.
- 자동 정지(구현된 것만 안전장치로 센다): §4의 강등, 형식 위반 연속 3건이면 그 인스턴스 `off`
  latch, 배정된 DM 무응답이면 그 질문을 운영자에게. latch는 운영자만 푼다.

## 9. 결과를 모를 때

worker에게 답을 전달한 결과가 불명확하면 다시 보내지 않는다. 카드를 운영자에게 보내고 DM의
답을 붙인다(원칙 7). DM 결정은 (카드 id, 질문 revision)당 하나이며, 같은 질문이 다시 와도
새 결정을 만들지 않는다.

## 10. 데이터와 법규

DM은 개발 작업 카드와 저장소만 읽는다. 사용자 콘텐츠·개인정보를 다루지 않으며, 새 사용자
데이터 모델을 만들지 않는다. 국외 이전 관점에서 질문 본문은 기존 worker와 같은 모델 공급사로
간다. 중국 본토 처리는 없다.

## 11. 단계

1. **S0 실측(유료 turn 포함, 운영자 승인 필요):** 서버의 `codex`로 GPT-6 Astra, `claude`로
   Fable 5.1을 계정에서 쓸 수 있는지, 두 CLI의 읽기 전용 모드가 쓰기를 실제로 막는지,
   구조화 출력이 스키마대로 나오는지.
2. **S1:** 라우팅(§3)·DM 결정 store·스위치(기본 `off`)·되돌릴 수 없는 행위 목록과 그 테스트.
   DM 호출 없음.
3. **S2:** 제안 모드 끝까지. 대시보드의 제안 확정·수정·거절과 DM 결정 목록. 서버 반영은
   운영자 승인.
4. **S3:** 졸업 기록과 자율 모드 스위치, 강등 latch.

각 단계는 독립 검토를 거치고, 앞 단계의 차단 기준(되돌릴 수 없는 것)이 통과해야 다음으로 간다.

## 12. 이 정책이 하지 않는 것

- 승인 계약, 오케스트레이션 정책의 게이트·승격·자동 승격·확인된 provider 목록을 바꾸지
  않는다.
- 터미널의 대화형 질문(`AskUserQuestion` 등) 화면에 키를 눌러 답하지 않는다. AMUX의 기존 규칙
  ("AskUserQuestion은 자동 응답하지 않는다")을 유지하며, DM은 board의 typed ask만 받는다.
- 도구 실행 승인(permission prompt)에 답하지 않는다.
