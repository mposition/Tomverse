## What it is

A per-agent Railway service that asks the app to publish, and a deadline that
actually stops a run. There is no publishing adapter until S2d2, so a run opens
its row, records why there is nothing it can do, and closes.

1. `prisma/migrations/20260923180000_marketing_publisher_run_deadline/` —
   `deadlineAt`, `heartbeatAt`, and a trigger scoped to rows carrying a deadline.
   Three refusals have their own SQLSTATE: `TMDL1` (a late run asking to be
   `succeeded`), `TMDL2` (a run starting after its deadline), `TMDL3` (a run
   reporting a sign of life after its deadline).

### The bounded-caller check: three versions, three shapes of question

This one guard was the blocker in all three rounds. Worth your attention, and
worth attacking hard.

- **v1** matched the text `runBoundedMarketingTransaction(` and then `prisma.`
  inside the argument. Broken by an aliased import (zero call sites) and by
  `const db = prisma` (a body with no `prisma.`).
- **v2** parsed the file and **banned** identifiers: the imported client under
  any name, the call's first argument, locals copied from either. Broken by
  `box.db`, `this.prisma`, a namespace-called wrapper, a parameter default,
  `globalThis`, an outside helper, `await import()`, and a client built from a
  dynamic import.
- **v3**, this round, inverts it. "Can this expression reach a client" is
  unbounded; "can this module obtain a client at all" is a decidable fact about
  its import declarations. So the body now gets an **allowlist**: its own
  parameters, anything it declares, a short list of globals, and imports from
  modules proven — transitively — unable to obtain a client. Dynamic
  `import()`/`require()` inside the body has its own rule, because `import` is a
  keyword and the binding it makes is an ordinary local.

  While checking this myself I found the same defect class one level down: 22
  files import the client as `../lib/prisma.ts`, and the pattern required the
  specifier to end at `prisma`, so it matched none of them. And in the other
  direction, treating every binding from `@prisma/client` as a client was wrong —
  `Prisma` is the namespace, `lib/modelLifecycleWorkItems.ts` re-exports it — and
  would have banned type-only modules from the body.

  I mutation-checked by putting real files in `lib/` and confirming each rule
  names them: `box.db`, a namespace-called wrapper, `../lib/prisma.ts` reached
  through a parameter default, a dynamic import, and a **three-deep** helper
  chain (`caller → two → three → prisma`).

  **What to attack.** Is the allowlist actually sound, or merely differently
  incomplete? Specifically: `SAFE_GLOBALS` — can anything on that list hand back
  a client, and is refusing everything else going to be unworkable for S2d2?
  Type-only imports are allowed wholesale — can a value arrive through one?
  `isFirstParty`/`resolveSpecifier` — what happens for a specifier that does not
  resolve (currently skipped, i.e. allowed), for a `.d.ts`, for a path alias this
  repo's tsconfig defines that my resolver does not know? `clientReach` treats a
  cycle as client-free on the second visit — construct a cycle that defeats it if
  you can. Does the walk see a client arriving via `export * from`? Does a
  `declare global` or an ambient module matter? And is the *call-site* detection
  complete — e.g. a call through an object property, an element access
  (`run["runBoundedMarketingTransaction"]`), or a re-export of the wrapper?

### The heartbeat and the deadline

A beat used to be the way to *hide* what the silence monitor watches for: the
service is force-killed at its deadline but the app route it called is not, and
that route kept beating, each beat moving `heartbeatAt` to the database's current
time. The trigger refuses a beat past the deadline now (`TMDL3`), read back
through `meta.driverAdapterError.cause.originalCode`, and the heartbeat returns
`{beat:true} | {beat:false, reason:"not_running"|"past_deadline"}`. The route
stops on either, closes the run failed with the reason, and answers 409 or 500.

Consider: can the route's two close paths both run? Can closing from the new
branch conflict with the trigger's own rules? **Is that error shape what Prisma
actually raises** for a trigger-raised custom SQLSTATE on `updateMany` — the
late-close path was dead for two rounds because a test built a shape Prisma never
produces.

### The silent-run read

Three wrong versions, each answering part of the question outside the database:
a predicate on `startedAt` alone; then an ordering by `heartbeatAt` when the
value compared is `COALESCE(heartbeatAt, startedAt)`, so a row that never beat
and started sixteen minutes ago sorted ahead of one whose heartbeat was ten hours
ago and the ten-hour row was the one cut; then a count and a page from two
snapshots, which can report ten while carrying evidence for one.

It is now one raw statement in `findSilentMarketingPublisherRuns`
(`lib/marketingPublisherRun.ts`). The fake that interpreted the query is gone —
it would have agreed with all three versions — and the predicate and ordering are
asserted against real PostgreSQL in
`tests/integration/marketing-automation-schema.db.test.ts`. Consider whether the
raw SQL is correct, whether `bigint` handling is right, whether the `LIMIT` and
the count really are one snapshot, and whether the integration test's scenario
would actually have failed the previous versions.

### The start-failure incident

A run that could not open its row left nothing anywhere: no row, so no silence
incident, and no delayed-job warning either, because `marketing_publisher` stays
in `PENDING_SCHEDULED_JOB_KEYS` until an operator applies the catalogue and a
first run is recorded. It reports `MARKETING_PUBLISHER_RUN_START_FAILED` now.
Consider whether a request that never arrives at all is observable anywhere, and
whether that is acceptable or a gap.
