# Tomverse Desktop

This workspace contains the Electron main process, a sandboxed preload and local Vite renderer, and a separate Code runtime process that bundles the existing Tomverse CLI headless entry. The approval window is owned by the main process. The renderer receives app capabilities through named IPC methods.

Desktop starts signed out. Once you connect your Tomverse account, Chat and Review can show your existing conversations. Availability of native actions depends on the account and server capabilities. The local integration fixture uses a temporary loopback server and profile and exercises the shared Code runtime. Standard packages exclude the fixture.

A connected Desktop Chat account reads its web history through the same conversation API. The server-side `TOMVERSE_DESKTOP_CHAT_WRITE_ENABLED` switch defaults off and requires Desktop authentication. Once enabled, Desktop uses the existing Chat model and credit checks for text questions. Deleting a conversation requires confirmation in the app.

`TOMVERSE_DESKTOP_REVIEW_ENABLED` also defaults off. It controls Desktop Review execution and authenticated image workspace requests. Review uses the existing routing, admission, and model entitlements. Image generation uses the server's catalogue and quoted price for each model and starts when the user confirms Generate.

## Run on your development machine

From the repository root, with the workspace dependencies and Electron binary installed:

```sh
npm run desktop:build
npm run desktop:start
npm run desktop:typecheck
npm run desktop:test:e2e
```

On Windows, the end-to-end test command runs Electron and native dialogs on a separate Windows desktop. The same launcher supports individual test files. It also gives the tests an empty home of their own (`HOME`, `USERPROFILE`, `CLAUDE_CONFIG_DIR`, `TOMVERSE_HOME` and `CODEX_HOME` point to a temporary folder, `scripts/test-home.mjs`), so the skills, hooks and MCP servers in the real home of the computer that runs them cannot change the tool lists the tests assert. The real home is passed as `TOMVERSE_TEST_REAL_HOME` for the one thing that needs it, the Windows sandbox, which keeps its files under the real profile. `TOMVERSE_TEST_USE_REAL_HOME=1` turns the isolation off.

```powershell
cd apps/desktop
node scripts/run-on-test-desktop.mjs --import tsx --test tests/desktop.e2e.ts
```

For the Desktop and mobile device-auth database regression suite, set `TEST_DATABASE_URL` to a dedicated, disposable loopback PostgreSQL database with a test marker in its name. Run `npm run desktop:test:db` to apply migrations, check for schema drift, and run the integration tests. The tests reset fixture tables in that database.

The package verifier checks the app archive, fixture exclusion, license notices, and runtime payload. For macOS it checks the architecture of the bundled executables and the app's files and framework links. On Windows it starts the packaged executable on a separate Windows desktop with a temporary profile to check the native window, taskbar icon, and Code worker.

```sh
npm run desktop:package -- --platform=win32 --arch=x64
npm run desktop:pack:verify
```

The packager targets Windows x64, macOS x64/arm64, and Linux x64. Local bundles go to `dist/package` under this workspace. macOS builds produced on a Mac are signed ad hoc for local use. After building the matching portable bundle, run `npm run desktop:package:native` on macOS to verify the app signature and create a local `.pkg`, or on Debian x64 with `dpkg-deb` to create a local `.deb`. Debian desktop testing requires a graphical session and Chromium user namespaces. Release signing and notarization require an Apple signing environment.

The packaged resources include `THIRD_PARTY_NOTICES.txt` with the bundled JavaScript dependency notices. Electron and Chromium include their runtime license files in the bundle.

After building the Windows x64 bundle, use a Windows SDK Developer PowerShell to make an unsigned MSIX. The build checks the executable against its ASAR, verifies the files in the generated package, and prints its SHA-256 hash. Set the publisher to the exact subject of the certificate used to sign the package. Pass `--makeappx` with the SDK executable path if it is unavailable on PATH. The MSIX must be signed with a trusted certificate before installation.

```powershell
npm run desktop:package:msix -- --publisher "CN=Your signing certificate subject"
```

To smoke-test profile compatibility on Windows, build a second version into a separate output directory with `desktop:package -- --out=dist/package/qa --version=0.1.1`. Run `npm --workspace @tomverse/desktop run pack:verify -- --out=dist/package/qa --previous "dist/package/Tomverse Desktop-win32-x64"` to launch both executables against a temporary profile and confirm that the older build can still open it. This exercises portable binaries. Test installer updates with signed packages.

Run the installed lifecycle test from the repository root in a disposable Windows user session. Provide two ascending MSIX versions signed with the same trusted test certificate. The test installs and launches the first version, checks that a real profile file survives the Windows package update, and checks uninstall and reinstall through the Windows package manager.

```powershell
powershell.exe -NoProfile -File apps/desktop/scripts/verify-msix-lifecycle.ps1 -Previous "<signed older MSIX>" -Update "<signed newer MSIX>"
```

On each supported Mac architecture, build two ascending local `.pkg` versions in separate output directories. Run the lifecycle verifier from the repository root in a graphical login on a disposable Mac with an empty Tomverse Desktop profile and a current sudo session. It validates both packages, installs them through macOS Installer, and checks that the installed window and its profile survive update and reinstallation. It keeps the test bundles and its JSON report in the printed temporary directory.

```sh
sudo -v
node apps/desktop/scripts/verify-mac-pkg-lifecycle.mjs --disposable --previous "<older pkg>" --update "<newer pkg>"
```

## Code projects and the environment picker

A **Code project** is a folder of this computer the person registered (`src/code-project-contract.ts`, `src/host/code-project-store.ts`, `src/host/code-project-host.ts`). It is a local list of the Desktop app, kept per account in `code-projects/<hash>.json` of the app's own data folder; it is not the web Chat project and nothing in it is sent to the server, so it has no server switch. A project has a name, an absolute folder (bound to the folder's canonical path; a network share is refused), a favourite mark, the time it was last used, a default environment (only Local can be applied for now: a cloud task needs the person's credit approval each time and an SSH project names its own remote folder, so those two are chosen from the picker), the permission mode last picked in it, and the Worktree box as last left in it.

- **Create project** (the start screen and the bottom of the history column) offers **New folder** (a name, and a choice to run `git init`; the main process then opens a folder dialog for the parent and makes the folder directly inside it, never anywhere else, and refuses a name with a separator, a drive or reserved name, or a trailing dot or space) and **Existing folder**. The window never names a path: the dialogs are the main process's. The first time an account opens the list, the folders it already opened (found from the history Code kept, and only in the account's own namespace for that folder) are moved in once.
- **The picker** under the composer (`<project> ▾`) lists **Local** (the projects: favourites first, then the most recently used; each with a star, the project's settings and a check for the open one), **Cloud** (Auto, Default), **WSL** (Windows only) and **SSH** (the recent remote projects, when remote projects are on), a search box that filters every group, and **New environment** (Create project, Add SSH remote). Arrow keys move over the rows, Enter chooses, typing goes to the search, Escape closes. A row that cannot be chosen stays in the list with its reason. Cloud is available only when the server reports `desktopCloudExecution` and the open project is a Git repository of this computer; because a cloud task needs the person to approve a credit cap, choosing it opens the Cloud tasks screen (Settings > Execution and limits) instead of sending from the composer. Code does not run inside a WSL distribution, so the distributions (read with `wsl.exe -l -q`, UTF-16 output) are listed switched off with the hint to open one as an SSH remote (localhost). Choosing another project while a conversation is open starts a new conversation; the project settings rename it, move its folder, set its default environment and remove it from the list (only the entry; the folder and its files are never deleted).
- **Worktree** next to the picker: on, the task runs in a separate Git worktree of the project (below). It is off, with the reason as its tooltip, for a folder that is not a Git repository with a commit, in Read only, and on a provider CLI route. The last choice is kept per project; a Git project starts with it on.
- **Tests.** `tests/codeProject.test.ts` (the register, folder checks, picker groups and their reasons, WSL parsing, the host), `tests/codeProjects.e2e.ts` and `tests/codePermissionPicker.e2e.ts`. The descriptor fields `projectFolders`, `projectParent` and `wslDistributions` answer the folder dialogs and `wsl.exe` in tests, where fixtures are allowed.

## Code workspaces

New Tomverse API Agent tasks in a Git project start in their own worktree when Git is on PATH. The **Worktree** box next to the project picker turns that on or off; with it on, a starting branch can be chosen, and the worktree path and working branch are shown before sending the task. The checkout starts at the displayed commit. With the box off the task edits the existing checkout, including local changes. Read only tasks use the open folder.

A worktree keeps the path relative to the repository of the folder you opened. Attachments for an isolated task must exist in the selected commit. After restarting Desktop, open the source folder and select the saved task from history to resume in its worktree. If the worktree is missing or on a different branch, Desktop blocks resumption and undo until the original checkout is available. Saved diffs and command details can still be inspected. Worktree files stay on disk when you delete Desktop task history.

## Permissions

The dropdown under the composer (`src/renderer/ComposerPermission.tsx`) replaces the old Agent / Ask / Plan select and the permission badge. It lists the four modes below with a line each, saves a pick at once with the same `set-mode` command Settings sends (the two share one state), asks for the confirmation of Allow all in place, and says when a change takes effect: for a running task, from its next tool call. A mode is remembered per project (Allow all is remembered as Ask), and a conversation in a project starts with it. Read only is what Ask and Plan used to be: the task reads, searches and answers, is not offered the tools that change files or run commands, and uses no worktree. Every other mode runs as an agent. Auto review and Allow all are for the Tomverse API route; on a provider CLI route they stay in the list switched off, with the reason, and a CLI route that can only read shows Read only alone. No screen starts a plan-only task any more; the engine still runs one for saved conversations and continuations.

**Settings > Task permissions** has the permission mode for Tomverse API Agent tasks and the allow, ask and deny rules. The modes are read only, ask each time (default), auto review (a separate model request judges each approval and is charged like any request; off by default) and allow all (asks for a confirmation, stays on show on the Code screen, and is not remembered after the app closes). Rules are saved by the CLI's rule store: user rules in the CLI configuration folder (`~/.tomverse/permissions.json`, or `TOMVERSE_HOME`) and project rules in `.tomverse/permissions.json` of the project; a project's own allow rules wait for your confirmation, and the confirmation is kept for the rules you were shown (a changed file asks again). A task in a managed worktree takes the confirmation of the project it was made from, but only when the allow rules in the worktree are exactly the ones you confirmed. **Allow for this run** on an approval card is remembered for that run only; a rule that lasts is one you add on this screen. Credential files, files outside the project and actions that leave the app (git push, pull requests, uploads) are never decided by a mode or a rule. The table below says what each mode decides; the CLI README has the same table with the details. The main process owns the mode; the Code runtime receives it as a message and nothing the model writes can change it.

| Request | read only | ask each time | auto review | allow all |
|---|---|---|---|---|
| File change, command | refused | approval window | a model request judges it | runs |
| Web page | approval window | approval window | approval window | approval window (a rule naming the site skips it) |
| Open a public site in the browser tab (agent) | approval window | approval window | approval window | approval window (no allow rule skips it; a deny or ask rule for the site applies) |
| Browser click or typing | refused | approval window | approval window | approval window (on a public site, one at a time: no "Allow for this run") |
| MCP tool | refused | approval window | approval window | approval window (a rule naming the tool or server skips it) |
| Agent commit | refused before the card opens | commit card | commit card | commit card |
| Agent push and pull request | refused before the card opens | push card | push card | push card |
| A subagent worker's change or command | refused | approval window | a model request judges it | runs |

A rule that denies always wins, an ask rule always asks, and a command that names something leaving the computer, a credential file or a path outside the project is never run without you. That check reads the command line (the CLI README says how); it does not see what a script, a package script or a repository's git alias does once it runs, which is what the command sandbox limits, and on Windows the sandbox does not limit the network. The agent's commit and push are off until you switch them on, and each call opens its own card in the main process, which the agent and every mode, rule and reviewer cannot answer: a push and a pull request need your approval every time, whatever the mode. A hook's "allow" is ignored in every mode, and a PreToolUse hook that blocks stops the call in every mode. Typing into a password, one-time-code or card field is refused by the browser tab itself in every mode.

## Browser panel: local pages, public sites, agent tools and element comments

The browser panel is the person's, and it is there in every build, in Chat, Review and Code alike, with no project needed: a globe button at the top right, just left of the theme button (a dot on it says the agent is working in a tab). It belongs to the signed-in account (or to the device when no one is signed in): it stays while you move between Chat, Review, Code and Settings, and signing out or switching account closes every tab and drops its session. Each tab has a session of its own, kept in memory only and dropped with the tab; none of it reaches the app's own session, so a site never sees your Tomverse account or another tab's cookies.

- **Two kinds of tab.** A *local* tab opens an `http` page on `localhost`, `127.0.0.1` or `[::1]` with a port and stays on that origin. A *web* tab opens a public `https` address (any port for a person): no other scheme (`file:`, `data:`, `javascript:`), no user name or password in the address, no IP address, single-word or local name (`.local`, `.internal`, `.lan`), and no plain `http` on a public name. A box with no scheme gets `https://`, or `http://` for a loopback address with a port. Every request of a web tab (the page, its redirects and everything it loads) must be `https`/`wss`/inline data to a public-looking name, and waits for the address check of `src/host/resolved-host-gate.ts`: a name that resolves to a private, loopback or link-local address is cancelled. That check cannot pin the connection to the address it checked (DNS rebinding can still make the connection attempt); the tab loads `https` only with certificate checks on, so such a page cannot read a local service's answer. A tab has no preload and no permissions (camera, location, notifications, clipboard, devices), no downloads, no sign-in or certificate dialogs, no client certificate (the app refuses `select-client-certificate` everywhere) and no WebRTC address exposure; a page's new window loads in the same tab. A page cannot be shared with Code (the share button is for local pages), and Chat and Review have no element picker.
- **The agent's switches.** The agent's tools are the person's choice: **Settings > Execution and limits > Let Code use the browser panel** (off by default; it applies to the next request of a running task as well, and the main process checks it again on every request). Under it, **Let Code open public websites in the browser panel** is a second switch, also off by default and meaningless without the first (`code-browser-web.txt` next to `code-browser-agent.txt`; a test fixture can set `browserWeb`). The element picker follows the panel itself.
- The Tomverse API agent gets `browser_navigate`, `browser_read`, `browser_screenshot`, `browser_console`, `browser_click` and `browser_type`. It drives one tab that its own task opened (never a tab the person opened), shown in the panel with a **Take over** button that ends its control at once; the agent's tab ends with its task. Without the second switch the addresses are limited to `http` on `localhost`, `127.0.0.1` or `[::1]` with a port, the same rule as the panel. With it, the agent may also open a public `https` site on the standard port (no other port, no IP address, no credentials): **each new site (host) is approved by the person first, in every permission mode** (the card shows the full address; "Allow for this run" covers that host for the run only, apart from `web_fetch`'s; no allow rule or saved answer skips it; a deny or ask rule for the host applies). The tab then stays on the sites approved for it: a page that moves to another site by itself (a redirect, a link, a form) is stopped, and the agent has to ask for that address, which asks you. While the agent holds a web tab, what you moved it to is neither read nor acted on until the agent opens that site again; take the tab over to browse freely. Reading, screenshots and console reads need no further approval; each click or typing is approved, and on a local page "Allow for this run" is remembered per site, while on a public site each one is asked on its own. Passwords, one-time codes and card fields are never typed. Page text is returned as untrusted data, marked as coming from a website. If you sign in to a site in the agent's tab, the agent can read what the site then shows you (the panel says so). The main process does the work: scripts run in an isolated world one call at a time, and input, pictures, the accessibility tree and the element picker use the tab's own DevTools session. Nothing is injected ahead of time.
- **Select element** lets the person click an element of the page, write a comment, and add several comments to the next message together. The message carries the selector, a short text and the position. The cropped picture of the element (the element's box only, at most 1600 px a side, PNG or a JPEG that fits 3 MB) stays in memory in the main process, and the first three pictures of a message go to the model with it, as one image message right after the instruction, when the model can see images (its catalogue entry says so; any other model gets the text only, as before). This works for a task start and for a follow-up sent while the task runs; a queued message and a provider CLI task carry text only. What names the picture is the line `picture pick-xxxxxxxx (attached as an image ...)` the app wrote into the message, so deleting that block from the box sends no picture. No picture is taken of a secret field (a password, card number or one-time code) or of any element with a visible secret field under its box; the panel says so and the message says `picture withheld`. With the agent's browser tools on, the same `pick-xxxxxxxx` id can also be read later through `browser_screenshot`. The image is an ordinary user-role image part of the model request, the same wire shape as `view_image`, so the server needs no change.

**Web search for the Code agent** (`web_search`) is off unless the server reports `desktopCodeWebSearch` (`TOMVERSE_DESKTOP_WEB_SEARCH_ENABLED`, the coding API on and a ready search backend on the server). The engine then calls `POST /api/code/v1/web-search` with the task's own Code key: Chat's web search, charged to the account at Chat's search price (one flat price per call of up to five queries, nothing when no search is served) and listed with the key's receipts. Every call is an approval card that shows its queries (the permission mode and a `web_search` rule decide as for a command; "Allow for this run" covers searches for the run, each still charged); it is answered at the PC only, never in a read-only or plan task, and never by a subagent. The addresses the search returned are shown in the task as its sources. `docs/policy/external-api.md` section 11.1.

## Window control: the agent sees and operates one desktop window

For apps and GUI tools the agent built or runs (not web pages: those are the browser tools' job). It is a switch, **off by default**: **Settings > Execution and limits > Let Code see and operate a window of my desktop**, and turning it on asks the person to confirm that the agent sees and operates the window they choose. Where the system has no implementation the switch says so and cannot be turned on. **Windows has the one that was run and checked**; Linux on an X11 session has another that has been **run only against a model of its tools in tests, never on a real X server** (see the last bullet below), so it is off unless the app is started with `TOMVERSE_DESKTOP_COMPUTER_UNVERIFIED_LINUX=1`; macOS has none. The Windows one is built and run here (PowerShell and .NET P/Invoke: window list, PrintWindow capture, SendInput; no native module, nothing installed). macOS (Screen Recording and Accessibility permissions) and Linux (X11 and Wayland) are "not supported" until someone has run an implementation there.

- **One window.** In Code, **Choose window** lists the top-level windows open now (title and program). The person picks one for this task; that choice is the agent's whole reach: never the screen, other windows, the taskbar or a system dialog. The choice is for that task (another task, another account or sign-out ends it), and **Stop sharing this window** revokes it at any time. Windows that are never offered, and cannot be chosen by id either, are in one list, `src/host/computer-deny.ts` (by program and window class, never by title; unit-tested): terminals and shells (they would run commands without the command approvals), browsers, password managers, system settings and administration tools, the system's own prompts (UAC, sign-in, credential dialogs), remote-control tools, the desktop shell, and Tomverse itself (by process id).
- **Tools** (Tomverse API agent only, and only for a model that sees pictures): `computer_screenshot`, `computer_click`, `computer_type`, `computer_key`, `computer_scroll`. The screenshot is the chosen window alone (PrintWindow, so a window in front of it is not in the picture), scaled to at most 1568 px on the long side; the agent's coordinates are pixels of that picture, which the main process maps back and checks against the window. The answer says if the window is behind another window or minimized. The picture goes to the model once, in the next request only: it is not written to the session or to any file, and the result is marked untrusted data. Keys are a fixed list (`src/computer-tools.ts`): Enter, Tab, Escape, Backspace, Delete, Home, End, PageUp, PageDown, the arrows, Space, Shift+Tab, Shift+arrows, Ctrl+A/C/X/Z/Y/S/F, Ctrl+Shift+Z, Ctrl+arrows. No Windows key, no Alt (so no Alt+F4), no Ctrl+Alt, no function keys, no system shortcuts, and no Ctrl+V (the clipboard cannot be checked).
- **Approval.** A screenshot needs none (the person chose the window). Every click, typing, key and scroll is approved in every mode by a person (read-only refuses; no rule and no reviewer can allow it), on a card that shows the window, the program and the exact action. "Allow for this run" is remembered for that window only. Not offered at all in read-only and plan sessions, in parallel tasks and in scheduled runs: only the open task, with the person in front, has them.
- **Before every action** the main process checks again, and the backend checks once more inside the same call right before the input is sent: it is still the same window (handle, process, class), not minimized, the same size as the picture, in front (the foreground window), nothing over it, and for a point that the pointer really is on the target (the result of placing it is checked, and it is checked again right before each click of a double click and each wheel input, so a pointer the person moved never carries a click into another window), that the window has not moved, and that the window itself is under that point. If any of that fails nothing is sent; input never goes to a different window. Only a window of Tomverse itself may hand the front back (the window is brought forward after the person's approval card closes); a window of any other program in front is the person's and is left alone.
- **Passwords and payments.** The window cannot be inspected from outside, so this is not enforced by the system: the tool descriptions and the card tell the agent to stop and hand over on such a screen, and text that the redaction function (`redactText`) would change (a key or token) is never typed. Do not choose a window that shows secrets.
- **Control.** While the agent works the Code screen shows it, with **Take control** (the agent stops at once) and **Let the agent continue**. A global key (`Ctrl+Alt+Shift+X`, registered while a window is chosen) stops it from any program; if it cannot be registered the agent can look but does not act. If the person touches the mouse or keyboard between the agent's own inputs (and not by answering an approval card) the agent stops (Windows `GetLastInputInfo`; the person's own typing in Tomverse counts too) and waits to be handed control back. After the agent's own input the watch compares Windows' own input clock: the backend reports the tick of the agent's last input, and the next action stops if the system's last input is more than one timer tick (about 16 ms) later than that, so the host's clock and the time the answer took to arrive play no part; input within one tick of the agent's own cannot be told apart from it. The backend reads that tick just before it calls `SendInput`, so nothing the person does after the input went out can be taken for the agent's, however long the backend is held up afterwards; the other way round, if `SendInput` itself took longer than a tick the agent's own input would count as the person's and the agent would stop. Only after the person's own click that the app is told of (an approval card, **Let the agent continue**, choosing the window) is there a longer grace of 400 ms, for the hand leaving the mouse. Taking a screenshot sends no input and so does not reset that watch: what the person did before the picture still stops the next action. Inside one action the backend looks again between its parts (each batch of typed text, the second click of a double click, the second wheel input) and stops there, saying how much went out. The stop key, **Take control** and **Stop sharing this window** also reach an input that is already being sent: the main process aborts the request, and the backend ends the PowerShell process it started (by its own handle, never by image name), so nothing further is sent; the next request starts a new process.
- **Linux (X11), not verified on a real session.** `src/host/computer-backend-x11.ts` drives the X11 command line tools (`xdotool`, `xprop`, `xwininfo`, `xprintidle` and ImageMagick's `import`; nothing is installed, an argument array is always used, nothing is written to a file). It starts only when the app is started with `TOMVERSE_DESKTOP_COMPUTER_UNVERIFIED_LINUX=1`, the session is X11 (a Wayland session, or a missing tool, means "not supported", not a weaker backend) and every tool answers. It keeps every safety device of the Windows one and the host does not know the difference: the same switch, confirmation and one chosen window; the same deny list (the Linux terminals, browsers, password managers, settings, authentication prompts, file managers and the panel and desktop are in it by program and by window class); every action checks, in this order, that the window is the same (X id, process, class), not minimized, the size of the picture, the active window (Tomverse's own window may hand the front back, no other) and not covered (every window above it in the stacking order and every window no window manager manages, such as a menu or a popup, is looked at, and what cannot be read counts as covering), a point must be inside, and the window under the pointer must be this window or a part of it; the pointer is put on the point and read back before each click and each few wheel notches, and a pointer the person moved ends the action; typing goes out in pieces of 24 characters with the window and the person's input checked between them; the person's own keyboard and mouse are noticed from the X server's idle time (the agent's own input is the baseline; input after the end of the agent's command and before the idle time was read is the person's; a person's input *while* a piece is being typed is only noticed at the next check); the same stop key, Take control and key list, and Ctrl+V is refused in the backend too. A picture is taken only of a window nothing covers (a grab of the screen under a covered window would carry what is above it), so there is none for a covered or minimized one. What it does not cover: Wayland, a window manager without `_NET_ACTIVE_WINDOW`, `_NET_CLIENT_LIST_STACKING` and `_NET_WM_PID`; an unmanaged window below the chosen one counts as covering (their order is not known) and one as big as the screen covers whatever it carries, because the compositor's overlay cannot be told from a window made to look like it, unless the person sets `TOMVERSE_DESKTOP_COMPUTER_X11_TRUST_OVERLAY=1` to say a property-less one is their overlay (on a compositing desktop the window therefore always counts as covered until they do); and the check and the input are separate program runs, so a window that changes between them is not caught as it is in the Windows script's single call. `tests/computerX11.test.ts` fixes each check against a model of the tools; **execution on a real X server is unverified.**
- Tests: `tests/computerHost.test.ts` (the deny list, the gate, coordinates, keys, mismatch, control; no real window), `tests/computerInput.test.ts` (what the generated script verifies before mouse input, and that aborting a request ends the backend process, with a stand-in program; sends no input), `tests/computerWindows.test.ts` (real windows on Windows: the picture is the window only, clicks, Unicode typing and keys land, nothing lands when covered, minimized, closed; it moves the real mouse, so it runs only with `TOMVERSE_COMPUTER_WINDOWS_TEST=1`), `tests/computerUse.e2e.ts` (a fake desktop: choose, picture, approval card, done).

## Code terminal

The terminal button in the Code header opens a terminal panel for the open task. It is off until you press **Turn on terminal**. Each task keeps up to four terminals, and their shells and scrollback stay alive while another task is on screen. They end when the task is deleted, when the project or account changes, and when Desktop quits, together with everything they started.

The app host owns the shells (the renderer only sends typed actions) and starts each in the task's folder, which is its worktree for an isolated task. A shell gets the basic command environment from `apps/tomverse-cli/src/env.ts` plus terminal settings, never a Tomverse session, an API key or a token. Terminals use the `node-pty` native module; the Windows and macOS packages unpack it next to `app.asar`. Without it (Linux, or a module that cannot load) the terminal falls back to a limited pipe shell and says so.

Code's own agent gets a read-only `read_terminal` tool for the terminals you leave shared with it (the **Code can read** toggle, on by default). It cannot type into a terminal, the output is returned as untrusted data, and commands still go through `run_command` and its approval. Select text in a terminal and press **Add to prompt** to attach it to your next request.

## Reviewing changes

A saved Tomverse API task has a **Review changes** panel under its conversation, also opened by typing `/review` (optionally `/review turn` or `/review branch`) in the instruction box. Choose the scope: uncommitted changes (the working tree against HEAD, with new files), the agent's last turn (from the task's own record), or the branch against its base. The main process computes each diff; the renderer only names a scope and, for a revert, the id of a hunk.

Click a line number to comment on it (Shift-click extends the range). **Add comments to the instruction** writes each comment into the instruction box with its file, lines and the code it is about. **Revert hunk** asks first, then writes through the same recorded edit as an agent patch, so the change appears in the task's list and the usual undo puts it back. It is refused when the file no longer has the hunk where the diff said, and credential files are never shown or sent to a reviewer.

**Run review** sends the diff to one or more models chosen from the Code catalogue. Each reviewer is a read-only Ask run (read tools only) through the same gateway, receipts and request limit as any Code turn; the dialog before it runs states how many models and requests may be used. Findings from all models are merged into one list that names the model behind each, and shown under the line they are about. A finding can be handed back to the agent from the panel.

Git runs with the same restrictions as the worktree code, with external diff and text conversion programs turned off. Desktop ignores global and system Git configuration, so a repository whose files are checked out with CRLF endings by a global `core.autocrlf` setting can show every line as changed.

## Drafting commit messages and pull requests

In the Git panel, **Draft with model** writes a commit message from the files you selected, or a pull request title and description from the branch, into the boxes you edit before committing or pushing. It is a read-only Ask run of a model you choose from the Code catalogue, through the same runtime, gateway, receipts and request limit as a Code task (`host/review-run.ts`): one model request, charged in credits like a Code task. The main process reads the diff itself (credential files are not shown), asks you in a native dialog first, and sends only the diff. A draft commits and pushes nothing; the push and the pull request keep their own approval card.

## Skills, commands and agents

Code reads the skills, commands and agent definitions written for Claude Code and Codex where they are: `.claude/`, `.agents/` and `.codex/` in the open project and in your home folder (the CLI README lists the exact locations and rules). Typing `/` at the start of a Code request lists the skills and commands (and `/review`, the one command the app handles itself, where a task can be reviewed); the task shows what you typed and the model receives the skill or command text, with its arguments filled in by the rules of the tool the file is written for. This holds for the first request of a task and for a follow-up, a queued message and the answer to a question the task asked. The text is guidance only: permissions, hooks and tool lists in the files are not applied, and every change and command is still approved in the approval window. Settings, under **Execution and limits**, lists what was read with its source path and what was not applied.

**Import from Claude Code / Codex** previews what those tools already hold for this project. Instruction files, skills, commands and agents are read in place, so only MCP servers from your own configuration (`~/.claude.json`, `~/.codex/config.toml`) can be copied, into `mcp.json` in the Tomverse CLI folder (`$TOMVERSE_HOME`, default `~/.tomverse`), in the same shape as a project `.mcp.json`. Nothing is selected by default, `env` and header values are hidden in the preview, and the values are read again in the main process when you confirm. Desktop does not start MCP servers from this screen.

## MCP servers and hooks on this computer

The Tomverse API agent uses MCP servers and hooks defined in files (formats, trust and limits: `apps/tomverse-cli/README.md`, "MCP servers and hooks"). **Connectors** (and **Settings > Execution and limits**) has a section "MCP servers and hooks on this computer", apart from the account's connectors: yours (`mcp.json` and `hooks.json` in `~/.tomverse` or `TOMVERSE_HOME`, Claude Code's user `settings.json`) and the open project's (`.mcp.json`, `.claude/settings.json`, `.codex/hooks.json`). A project's server or hook waits for **Approve**; the approval names the definition's hash, so one that changed since the list was shown is not approved, and a changed one asks again. Each can be switched off, and **Check connection** starts an approved server to count its tools (an unapproved one is never started to be looked at). The window sends typed commands only (`local-extensions-contract.ts`), never a path or a command line. Each MCP tool call opens the usual approval window with the server, the tool and the arguments. Read-only and Plan tasks start no servers.

## Command sandbox

Settings > Execution and limits > Command sandbox limits what the commands Code runs can change: `workspace-write` (the project folder and a temporary folder), `read-only`, or `off` (the default), with an editable list of sites a command may reach through a filtering proxy. The screen shows what the current operating system really enforces. Windows limits writes only; its network list is advisory. The method, its limits and what it changes on disk are in `docs/ops/desktop-sandbox.md`. The sandbox applies to the Tomverse API path and is read again when each task starts. The settings screen says so.

## Cloud and managed credits

**Cloud tasks** (`docs/ops/desktop-cloud-execution.md`; **off unless the server reports `desktopCloudExecution`**, which needs `TOMVERSE_DESKTOP_CLOUD_EXECUTION_ENABLED`, `CODE_MANAGED_EXECUTION_ENABLED` and a runner secret on the server, and a deployed runner to do anything): the same section then lists Tomverse cloud as available and shows **Run in Tomverse cloud** (`src/renderer/CodeCloudTasks.tsx`). Starting one makes a git bundle of the open project's tracked files without files that look like credentials (`src/host/cloud-bundle.ts`, nothing in the repository changes), creates the job and uploads the bundle over the account settings session (`src/host/cloud-execution-client.ts`), and follows its state and progress lines (`src/host/cloud-execution-host.ts`). Credits are the server's managed reservation; Desktop shows receipt numbers only. The renderer can name only `read`, `start`, `cancel`, `review`, `apply` and `closeReview` (`src/cloud-execution-contract.ts`).

## Remote projects over SSH

**Settings > Execution and limits > Remote project (SSH)** (**off by default**; when it is off the start screen shows nothing remote, the runtime refuses a remote project even if one is selected, and no ssh is started) lets the Tomverse API agent work on a folder of another computer: a dev server, a devbox. The agent still runs here (the model key, the permission modes and rules, the approval cards, the journal and its backups all stay on this computer); only its file reads, edits and commands go to the other computer, through **your own `ssh`** with your `~/.ssh/config`, ssh-agent and known_hosts. Design, the remote protocol and the limits: `apps/tomverse-cli/README.md`, "Remote projects over SSH".

- **Open one.** With the switch on, **Remote project (SSH)** on the Code start screen (or the form in Settings) takes the SSH target (a Host name from `~/.ssh/config`, or `user@host`), an optional port and the absolute folder on that computer. **Test connection** says which step failed: no ssh program, the key could not be used without asking (connect once in a terminal and add the key to ssh-agent), the host key is unknown or has changed (check it yourself in a terminal; the app never accepts an unknown host, whatever `~/.ssh/config` says: the strict check is given to ssh on the command line), the name or the network, a missing folder, a folder that is too broad (the root, the home folder, `.ssh`, `.git`), a machine without a POSIX shell and the usual tools. **Open as project** tests again and opens the folder as the project. The app never asks for, receives or stores a key, a password or a passphrase; ssh is always started with `BatchMode=yes`. **Command shell**: for the open remote project, Settings can switch how the agent's commands are started there from `sh -c` (default) to `bash -lc`, which reads the profile of your account on that computer first (so tools a profile puts on `PATH` are found; what the profile prints appears in the command's output). It applies to the next task, is kept per project in the Desktop's own settings and never in a project file, and only commands use it, never file reads or edits.
- **What is checked in the main process** (`src/remote-contract.ts`, `src/host/remote-project-host.ts`): every part of the target (an option cannot be injected: no leading `-`, no spaces, control or shell characters in the target; the folder is absolute, without `..`), the switch, and that no task is running. ssh gets an argument array, never a shell string.
- **What a remote project is on this computer.** An empty folder of the app's own (`Tomverse Desktop Remote Projects/<hash>`, outside the app data folder) with a marker that names the target stands for it in everything that keeps a folder: history, the one-task-per-project lock, permission rules, notes. The marker counts only inside that folder and only if its name was made from the target in it, so a repository cannot name a machine. Nothing the agent reads or writes is ever looked for in that folder.
- **Approvals.** A patch or command of a remote project goes through the same approval card, permission mode and rules as a local one, and the card shows **On a remote computer: `<target>`** with the remote folder and the remote paths. The command sandbox does not cover it: with the sandbox on, the project screen says so, and the card says commands there run outside it. For a schedule, a remote project counts as having no sandbox (so "allow all" is refused for it).
- **Connection.** One ssh run per operation (Windows' OpenSSH has no connection sharing, and nothing depends on it). If the connection goes, the status above the composer reads **Connection lost**, every further write or command is refused with that reason, a command running there is ended by the remote machine itself, and **Reconnect** brings the project back so the task can be continued. A remote write is a temporary file and one rename, so a dropped connection never leaves a half-written file.
- **Not offered for a remote project** (they work on a folder of this computer; the status says so instead of breaking quietly): the terminal, the review panel, the Git panel and pull requests, worktrees, attaching local files or folders, background commands, orchestration, provider CLI routes, the git tools of the agent, project-level MCP servers and hooks. Changes of a remote task are listed with their diff and **can be undone one at a time** (checked against the remote file); rewinding a task puts back the conversation only.
- **Tests.** `tests/remoteProject.test.ts` (settings, shadow folders, the host, the runtime's change view and undo) and `tests/remoteProject.e2e.ts` run against a fake ssh (`apps/tomverse-cli/tests/fake-ssh.mjs`, a stand-in that runs the remote command through the local `sh`, with a folder of this machine as the remote one); no real SSH server is involved. The descriptor field `sshFixture` is read only where Desktop fixtures are allowed.

## Plugins

**Settings > Execution and limits > Plugins** installs, updates and removes plugins and adds marketplaces (formats, trust and limits: `apps/tomverse-cli/README.md`, "Plugins and marketplaces"). The window sends typed commands only (`plugins-contract.ts`); the folder to install from is chosen in a dialog the main process opens, and only the id of a preview the main process made can be confirmed. An install or update shows a **preview first**: counts, names, and every hook and MCP server command in full (an update also what is added, removed or changed); nothing is installed until **Install**/**Update**. A download from a git address asks in a native dialog first, naming the address. A plugin's hooks and servers appear in "MCP servers and hooks on this computer" with the plugin as their origin and wait for **Approve** (bound to the digest of the plugin's files). Each plugin can be switched off for everything or for the open project.

**More places to install from, behind `TOMVERSE_DESKTOP_PLUGIN_SOURCES_ENABLED`** (default off; the `desktopPluginSources` capability, which needs only the Desktop session and is independent of `TOMVERSE_DESKTOP_PLUGINS_ENABLED`, the switch for server connectors). With it on, the Plugins screen also installs from a **zip file** (picked in a dialog), the **address of a zip file** (https only), an **npm package** (`name` or `name@1.2.3`; an exact version or none for the newest, never a range or tag) and a **private github.com repository**, and it adds the **Tomverse official marketplace** the app carries (`src/official-marketplace.json`, empty for now; written into the Tomverse folder and added like any marketplace; a checkbox turns it off for good). All of them go through the same preview and confirmation as a folder, and a download is asked about in a native dialog first, naming the address (no query: a signature is not shown or kept). An archive is unpacked by this app, not by a tool: an entry that climbs out of its folder, uses a backslash or a drive letter, or is a link or special file is refused, as are archives past 50 MB, 5000 files, or 10 MB for one file, and the sizes an archive declares are checked against what it really holds. npm is never run: the registry is asked for one version, the tarball is checked against the registry's sha512 integrity value (and the one a catalog pins) and unpacked as plain files, so no install script starts; the integrity value or the zip's SHA-256 is shown in the preview and is part of the digest the confirmation covers. A private repository is read with the GitHub CLI sign-in the person already has (the one the Git and pull request features use): after a public attempt fails and the person agrees in a native dialog, git is told to ask `gh auth git-credential` for github.com only. Desktop never receives, stores or logs a token (nothing is added to the OS keychain), and an error text that looks like a token is masked. A record of a plugin from one of these places is stored as `source: folder` plus an `origin` field, so an older copy of the CLI sharing the Tomverse folder still reads the file. Turning the switch off hides these sources and refuses them; plugins already installed keep working.

## Subagent orchestration

**Settings > Execution and limits > Subagent orchestration** (off by default; a per-task switch like goal mode, kept in this window and applied to new tasks) lets the Tomverse API agent split a large job into subtasks that run in parallel. The setting shows what it may use, "up to 3 subagents at once, 90 requests in all", and each run says it again in the task. It is the CLI's `delegate` extended (`apps/tomverse-cli/README.md`, "Orchestration"): the same gateway, requests and credits as any request, nothing priced separately, and the task's own request limit still applies (the Standard profile's 20 requests fit only small subtasks; choose Extended for a large job).

The Code screen gets a **Subagent activity** list: each subtask with its state, its newest step, the files it declared it may change, the files it changed, how many requests it used and how its result was verified (a read-only verifier against the completion criteria, plus a declared check command when there is one). **Stop** ends one subtask, **Stop all subagents** ends them all; the main task goes on and is told. Stopping the task stops everything. A worker's change or command is asked in the usual approval window, one at a time, saying which subtask asks. The window sends typed actions only (`orchestrate-contract.ts`): the switch, and a subtask id or "all" to stop. Read-only and Plan tasks get no worker subtasks.

## Parallel tasks and scheduled runs

**Parallel tasks.** The task the window has open runs in the main Code runtime. Every other task (started from the activity button in the Code header, or by a schedule) runs in a runtime process of its own, one process per task, so a task that fails, hangs or crashes cannot touch another. The rules are in `src/host/task-lanes.ts` (no Electron, unit-tested): at most **3** tasks run at once (a setting in the activity list, 1 to 6, kept in `parallel-limit.txt`; the open task counts) and the rest wait in a queue; two tasks never write the same folder (a task in its own new worktree has a folder of its own, and the existing workspace lock still refuses a second writer); each approval belongs to the task that asked, is labelled with that task's name and folder, is shown one at a time, and is answered only through the lane that asked (`answer()` in `main.ts` hands a lane's card to `lanes.decide`, which posts it under that lane's run id). An agent's commit or push from a lane uses the same ticket ledger on that lane's own folder, and its card goes to the same queue. A lane has no browser tab, terminal or plugin bridge. Limits per task (`limits` on the start input) and the account's credit limits are unchanged, so running tasks at once does not raise any of them. Quit stops every lane (and kills its process tree) before the app closes.

**Activity view.** The activity button lists the open task, the parallel tasks and the scheduled runs with a line each (waiting for a slot or its folder, running, waiting for approval, or how it ended), with Stop, Open, Side by side (two tasks next to each other), Own window and Remove. A task's own window (`/task`) has a preload of its own (`taskHost`: read and stop); the main process binds the window to one task by the window's id, so the page never names a task and no `desktop:` channel is reachable from it.

**Scheduled runs** (`src/host/schedule-engine.ts`, `schedule-launch.ts`; the arithmetic is `src/schedule-core.ts`, the safety rules `src/schedule-policy.ts`). **Off by default**; **Activity > Schedules** turns them on after the person reads that a run starts at its time with nobody confirming and uses credits. A schedule has an instruction, a repeat (once, every N minutes, daily, weekly) in a time zone, the project folder open when it was saved, where it runs (that folder or a new worktree), a permission mode and a request cap (standard 20 or extended 200, never unlimited). They run only while the app runs; there is no OS service or login item. A run that came due while the app was closed is recorded as **missed** and not made up; a run that is late by more than five minutes while the app runs is missed too. Each run is recorded (times, status, changed files, the task to open), and an OS notification is sent when it ends. Rules enforced in the main process: a request that needs a person is never answered for them and no card opens by itself, the run waits as "waiting for approval" in the activity list and fails after 30 minutes; a push or a pull request always needs the person's approval card (the agent's git tool, and a `git push` or `gh` command, which the permission boundary leaves to a person in every mode; on Windows the sandbox's network list is advisory, so a program the agent writes and runs itself is not stopped by it); **allow all** is accepted only for a new worktree run on a computer whose OS sandbox really refuses writes outside the project (checked again at every run); a schedule turns itself off after 3 failed runs in a row; schedules belong to the account that turned them on (another account sees none and starts from nothing); one schedule never runs twice at once. The agent has no tool that reads or changes schedules; they change only through typed commands from the window (`parallel-contract.ts`). Daylight saving: a wall time skipped by the clock change runs right after the gap, a repeated one runs once, at its first occurrence.

## Control from other devices

**Settings > Execution and limits > Allow control of this PC from other devices** is off by default, applies to the signed-in account only, and asks in a native dialog before it turns on. It also needs the server switch `TOMVERSE_DESKTOP_REMOTE_CONTROL_ENABLED`. While it is on and a Code task runs, the main process reports a short, redacted summary to the server: every 8 seconds, or every 2 seconds while a request that may be answered from elsewhere is open. The person can then use `tomverse.app/remote` on a phone or another computer to watch the tasks, answer the approval request on the PC's screen (allow once or deny), stop a task, or send the open task a follow-up. Nothing is sent while nothing runs, and the PC always opens the connection itself.

The rules are in `src/host/remote-control.ts`, which has no Electron and is unit-tested. The settings screen says what is sent: titles, states, the first prose line of recent messages, and for the open request its kind and its command line or file paths. File contents, diffs, command output, environment values and credentials are not sent.

The approval is still decided here. An answer from elsewhere is applied only through the approval window's own `answer()`, and only when all of these hold:

- it is for the card on screen now, with the same digest of the whole request
- it is "allow once" or "deny"
- it is not a repeat
- it is younger than 2 minutes and names this device

Only file changes whose paths are all shown, and commands whose whole line is shown and that the permission boundary does not leave to a person, may be answered from elsewhere. Commits, pushes and pull requests, MCP tools, web pages, the browser panel, "Allow for this run" and every setting stay at the PC.

Turning the setting off or signing out deletes the server's copy. The server side is described in `docs/ops/desktop-remote-control.md`.

## Update channel

### Windows Local Dev

**Tomverse Desktop Local Dev** is a Windows x64 test package that connects to `dev.tomverse.app`. It has its own Windows package identity and app profile. Windows App Installer checks its local `.appinstaller` file at launch. Keep the channel directory at the path registered during installation.

From the repository root on the Windows packaging PC, use PowerShell 7 with Node.js and the Windows SDK x64 MakeAppx and SignTool installed:

```powershell
$channel = 'H:/Project/tv-desktop-agent-worktrees/local-dev-updates'
./apps/desktop/scripts/package-local-dev-update.ps1 -Version 0.1.130 -ChannelDirectory $channel
```

The script signs the new MSIX with the Local Dev key in the Windows current-user certificate store and updates the local channel only after checking the signature, package identity, and version. The private key stays non-exportable in the certificate store. Use `-BuildOnly` to prepare a package before updating the channel.

When creating a channel, the first run exports the public `Tomverse-Desktop-Local-Dev.cer` and stops if it is untrusted. Import that certificate into **Local Computer → Trusted People** with an administrator account, then rerun the build. Open `Tomverse-Desktop-Local-Dev.appinstaller` once on the test PC to enroll the app. After publishing a higher version, open **Tomverse Desktop Local Dev**: App Installer installs the update before the app starts (`ShowPrompt` with `UpdateBlocksActivation`), and a background task also checks while the app is closed. A check made while the app is already running cannot replace it and fails with `0x80073D02`; the feed before 0.1.140 checked only at launch, so every update from 0.1.129 to 0.1.140 failed that way. A PC still on such a build installs once by hand with the app closed: `Add-AppxPackage -AppInstallerFile <channel>\Tomverse-Desktop-Local-Dev.appinstaller`.

The Dev server advertises two additional capabilities after their server switches are enabled. `TOMVERSE_DESKTOP_COMPOSER_TOOLS_ENABLED` enables Chat's conversation-scoped web search, assistant and memory controls alongside Desktop Chat writes. `TOMVERSE_DESKTOP_REVIEW_ANALYSIS_ENABLED` adds the answer-analysis dialog for two or more saved text answers alongside Desktop Review writes. The analysis uses the existing `GET` and `POST /api/conversations/{conversationId}/comparison-reviews` and keeps its server-side ownership and credit checks. `TOMVERSE_DESKTOP_REASONING_STEPS_ENABLED` (with `TOMVERSE_REASONING_EFFORT_ENABLED`) adds the Medium reasoning step to Chat, Review and, through the coding catalogue, Code, for the models that take an effort; Desktop offers it only for models whose catalogue entry lists it and only when the server names `desktopReasoningSteps`. `TOMVERSE_DESKTOP_PROMPT_REFINER_ENABLED` lets an Auto Chat turn carry the Prompt Refiner decision the server holds (`desktopPromptRefiner`; `src/host/prompt-refiner.ts`): the Refiner is automatic and has no panel, the main process writes the typed text as the conversation draft, asks the server for one preparation over the account settings session, and sends only the returned decision.

`TOMVERSE_DESKTOP_REVIEW_DEEP_RESEARCH_ENABLED` (default off, on top of Desktop Review writes and the Perplexity key Deep Research already needs) adds Deep Research to the Review "+" menu in Professional mode. A run is one more column of the Review, put to the Deep Research model alone through the Chat route (the question is saved for that model only, there is no shared admission, and the price is the model's own, unchanged). The Review then holds the models the composer shows plus Deep Research, so it needs a free place among the plan's models; a new Review keeps the first models that fit beside it. The result is polled through `POST /api/chat/deep-research/status`, which accepts a Review only under this switch. The Desktop build offers the row only when the server names `desktopReviewDeepResearch`.

### Release builds

Release builds can embed a deployment-controlled HTTPS origin through `TOMVERSE_DESKTOP_UPDATE_ORIGIN` at build time. The feed endpoint is `/desktop/updates/{platform}/{arch}/{currentVersion}`. The packaged Windows path requires a signed, directly installed MSIX. Windows App Installer manages updates for packages installed through an App Installer manifest. The macOS path uses Electron’s native updater with a signed app and JSON feed. Linux updates follow the supported distribution package path.

For Windows x64, the stable feed returns HTTP 204 when no update is available. Return an update for a newer numeric `x.y.z` app version with the fields below. Use the exact byte count and lowercase SHA-256 of the final signed MSIX at a direct HTTPS URL on the feed origin. The MSIX uses the corresponding `x.y.z.0` package version. Windows verifies the downloaded signature, and the app checks the signer and package identity against the installed package before staging it with Electron.

```json
{
  "channel": "stable",
  "platform": "win32",
  "arch": "x64",
  "version": "0.1.1",
  "url": "https://updates.example.com/releases/Tomverse-Desktop-0.1.1.0-x64.msix",
  "size": 180000000,
  "sha256": "0123456789abcdef0123456789abcdef0123456789abcdef0123456789abcdef"
}
```

The app checks periodically when an update channel is configured. Settings shows download readiness and prompts for a restart. Active Code tasks and Chat writes prevent installing the update. Signed updates, feed responses and cross-version installation require release artifacts and separate verification.

For macOS, the endpoint returns the stable Squirrel JSON manifest for the requesting architecture. The top-level manifest includes `channel: "stable"`, `platform: "darwin"`, `arch`, `currentRelease`, and `releases`. The selected `updateTo` entry includes a matching version, a same-origin HTTPS ZIP URL, the ZIP byte count and its lowercase SHA-256. The app passes the validated entry to Squirrel as a local file and keeps it until the native check finishes. Native signature and downgrade checks apply when Squirrel opens the ZIP.

On a Mac with a matching Developer ID signed and stapled app, create the update ZIP and `releases.json` from the repository root. The script validates the bundle, package architecture, signature, and notarization ticket before writing a versioned output directory. Serve the generated JSON at the version-specific feed path and the ZIP at the URL declared in the feed.

```sh
npm run desktop:package:native -- --out=dist/package --update-origin=https://updates.example.com
```
