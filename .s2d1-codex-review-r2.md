## What it is

A per-agent Railway service that asks the app to publish, and a deadline that
actually stops a run. There is no publishing adapter until S2d2, so a run opens
its row, records why there is nothing it can do, and closes.

1. `prisma/migrations/20260923180000_marketing_publisher_run_deadline/` —
   `deadlineAt`, `heartbeatAt`, and a trigger scoped to rows with a deadline.
   Two refusals carry their own SQLSTATE: `TMDL1` (a late run asking to be
   `succeeded`) and `TMDL2` (a run starting after its own deadline).
2. `lib/marketingPublisherRunCore.ts` — the timing numbers and the pure rules.
3. `lib/marketingPublisherRun.ts` — start / heartbeat / finish, and
   `runBoundedMarketingTransaction`.
4. `app/api/internal/marketing-publisher/route.ts` — bearer auth, strict body,
   the run's lifecycle.
5. `scripts/run-marketing-publisher.mjs` (supervisor: run id, deadline, spawn,
   SIGKILL at the deadline) and `scripts/marketing-publisher-worker.mjs` (one
   request, no retry).
6. `.railway/scheduled-jobs.ts`, `lib/scheduledJobsCore.ts` — the service, its
   cron, and the job key in `PENDING_SCHEDULED_JOB_KEYS`.
7. `lib/infrastructureThresholdMonitor.ts` — the silent-run incident.
8. A separate commit moves both CI database lanes to `postgres:17-alpine`.

## What round 1 found, and what changed

You reviewed this and returned `reject` with seven findings. All seven are
addressed. **Check each fix on its own terms — a fix is a new change and can be
wrong in a new way.** What I claim:

1. **blocker, the trigger's immutability hole.** Adding a *past* `deadlineAt` to
   an existing `succeeded` row with `deadlineAt = NULL` passed both branches and
   produced `completedAt > deadlineAt`. The check no longer looks at whether the
   row already had one: on `UPDATE`, any change to `deadlineAt` is refused. A
   deadline now comes only from the insert that opened the run. New integration
   cases: "a deadline cannot be added to a row that does not have one" (closed
   row, running row, past deadline and future deadline) and "an ordinary
   scheduled job row is still writable end to end".
2. **blocker, work that reaches past its `tx`.** Nothing in-process can stop a
   callback that closes over the module-level `prisma`: it is another
   connection, and its writes can commit after this transaction rolls back. The
   comment that acknowledged this is gone; the escape is refused in source, by
   `tests/marketingPublisherBoundedCallers.test.mjs`, which extracts each
   `runBoundedMarketingTransaction` call's work argument with a
   string/comment-aware balanced scan and refuses `prisma.` and `$transaction`
   inside it. There are no callers yet — S2d2 writes the first — so the gate
   exists before the code it constrains. **The scanner is the thing to attack**:
   if it can be made to return a truncated or empty body, the gate is theatre.
   Its third test plants a call and asserts the body is read whole; decide
   whether that is enough.
3. **major, `set_config` on an already-armed `transaction_timeout`.** You were
   right, and I did not verify it either way before. The wrapper now reads
   `current_setting('transaction_timeout')` inside the transaction and refuses
   with `transaction_timeout_already_armed` unless it is `0`/`0ms` — including
   when the pre-existing bound is *shorter*, because a bound this function
   cannot state is not one it can keep. An unreadable answer is refused too.
   Consider: are `0` and `0ms` the only spellings `current_setting` returns for
   off? Is refusing the right answer, or should it use the smaller of the two?
   Does this make the publisher unrunnable on a deployment that sets the GUC at
   role level — and is that acceptable fail-closed behaviour or a foot-gun?
4. **major, a failed run reported as HTTP 200.** The route now answers 500 with
   `code: "run_closed_late"` when the close did not return `succeeded`, and
   reports `MARKETING_PUBLISHER_RUN_LATE`. The worker additionally exits 1 on
   any 2xx whose body says the run did not succeed.
5. **major, the error path recorded nothing.** The route reports
   `MARKETING_PUBLISHER_RUN_FAILED` with the original error *before* attempting
   the failure-close, and both the report and the close log their own failures
   rather than being swallowed.
6. **major, the red server-contract gate.** The mock lacked `findMany` and the
   expected payload lacked `silentPublisherRuns`. Fixed, plus two new cases: a
   silent run pages and is counted, and a silence check that cannot read records
   `null` rather than `0` and pages nothing.
7. **minor, `alerts` disagreed with what was reported.** `alerts` now includes
   the publisher incident.

## What to look for beyond the fixes

The failure shape this feature keeps producing is **a test whose fake agrees
with the code and disagrees with the real dependency**. It has happened at least
five times here, including once in the round-1 material you reviewed. Of the new
code:

- `tests/server-contract/marketing-publisher-route.test.ts` mocks
  `lib/marketingPublisherRun.ts` entirely. Does anything it asserts depend on
  that mock returning a shape the real function cannot return? In particular,
  `finishMarketingPublisherRun`'s real return type — does the route's new
  `closed.status !== "succeeded"` branch cover every value it can actually take?
- The transaction test's fake now answers a `current_setting('transaction_timeout')`
  probe. Does it match the real statement, and could the real one return
  something the fake never produces?
- The new static scanner: does it agree with what the TypeScript compiler
  considers a call to that function? Aliased imports, re-exports, a call split
  across a variable.
