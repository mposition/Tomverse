## What it is

A per-agent Railway service that asks the app to publish, and a deadline that
actually stops a run.

1. `prisma/migrations/20260923180000_marketing_publisher_run_deadline/` — adds
   `deadlineAt` and `heartbeatAt` to `ScheduledJobRun` plus a trigger scoped to
   rows that carry a deadline. Two refusals have their own SQLSTATEs: `TMDL1`
   (a late run asking to be `succeeded`) and `TMDL2` (a run starting after its
   own deadline).
2. `lib/marketingPublisherRunCore.ts` — the timing numbers, the ordering rules
   between them, the batch-room rule, the start-deadline check, the silent-run
   rule, the request schema. No Prisma, no `server-only`.
3. `lib/marketingPublisherRun.ts` — start / heartbeat / finish, and
   `runBoundedMarketingTransaction`, which sets three timeouts via
   `set_config(..., true)`, refuses below PostgreSQL 17, and counts statements
   with a Proxy.
4. `app/api/internal/marketing-publisher/route.ts` — bearer auth, strict body,
   opens the run and closes it with the reason there is nothing to do (no
   publishing adapter exists until S2d2).
5. `scripts/run-marketing-publisher.mjs` (supervisor: generates the run id and
   deadline, spawns the worker, SIGKILLs it at the deadline) and
   `scripts/marketing-publisher-worker.mjs` (one request, no retry).
6. `.railway/scheduled-jobs.ts` and `lib/scheduledJobsCore.ts` — the service,
   its cron, and the job key, which sits in `PENDING_SCHEDULED_JOB_KEYS`.
7. `lib/infrastructureThresholdMonitor.ts` — the silent-run incident.
8. A separate commit moves both CI database lanes to `postgres:17-alpine`.

## What a previous reviewer already covered

A different reviewer passed this over three rounds and ended with `approve` and
no findings. Its findings, all fixed, were: a close that reported success
without checking it closed a row; a start refused by the database surfacing as a
framework 500; the late-success refusal matched by message text rather than
code; a nested `$transaction` escaping the statement budget; the worker
inheriting the whole process environment.

That reviewer also **missed one thing for two rounds**, which the author found:
the SQLSTATE match read `error.cause`, and Prisma's `P2039` has no `cause` — the
code is at `meta.driverAdapterError.cause.originalCode`. The unit test "proving"
that path built an error with a `cause` shape Prisma never produces, so it
passed while the path was dead.

**Assume nothing on that reviewer's word.** Your value here is finding what it
did not. Look especially for more of that same shape: a test whose fake agrees
with the code and disagrees with the real dependency.

## Questions worth your attention

1. **The trigger.** Walk every path: insert with and without a deadline; update
   while running (heartbeat, close on time, close late, close failed); update
   after closing; attempts to move or null the deadline. Can a late run be
   recorded `succeeded` by any route through it? Can it break any existing
   scheduled job that writes `ScheduledJobRun` without a deadline, including
   `completeScheduledJob`, `failScheduledJob` and the auto-fix fields?
2. **`set_config(name, value, true)`.** Is it genuinely equivalent to
   `SET LOCAL` for *arming* `transaction_timeout` on a transaction that is
   already open, on PostgreSQL 17? Is a bare integer string milliseconds? If you
   cannot establish this from documentation or source available to you, say so
   rather than assume either way.
3. **The ordering of the three timeouts.** `transaction_timeout` is set to the
   derived maximum (115 s) and the two ceilings to 5 s. Is that correct for
   keeping both armed, and does `marketingPublisherTimingProblems` actually
   catch every ordering that would silently disarm one?
4. **The statement counter.** Does the Proxy count every statement the work can
   issue? Consider `$executeRaw`, delegates reached through a destructured
   variable, `include` (one call, more than one SQL statement), a method whose
   thenable is not awaited, and work that reaches for the module-level `prisma`
   instead of the `tx` it was given. The plan calls the derived maximum an
   application figure — is the code's claim no stronger than that?
5. **The route.** Bearer comparison, body strictness, the deadline acceptance
   window, duplicate run ids. The route judges the deadline with the process
   clock and the trigger with the database's — where does that difference land?
6. **The service.** Does the supervisor kill in every case, including a worker
   that ignores signals or one that never spawns? Does the worker retry
   anywhere? Can either hold anything beyond its two declared variables?
7. **PostgreSQL 17 in CI.** The plan prefers it over asserting a bound nothing
   tests. Is anything in this repository likely to behave differently on 17 in a
   way that would redden a lane?
8. **The tests.** Do they prove what they are named for? There is no local
   PostgreSQL here, so read the integration tests against the migration rather
   than running them.
